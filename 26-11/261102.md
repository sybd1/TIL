# 2026-11-02 TIL — JPA, 영속성 컨텍스트, 엔티티 생명주기와 JUnit

> 수업 메모와 `10_jpa-main`의 입문·영속성 컨텍스트 코드를 바탕으로 정리했다. 메모의 빈칸과 혼동한 부분은 Jakarta Persistence, Hibernate, JUnit 공식 문서로 확인했다. 코드 예시는 해당 단원의 Menu 엔티티를 기준으로 하며 필요한 import 등은 생략했다.

## 1. 먼저 정리할 핵심

- **JPA**는 자바 객체를 관계형 DB에 저장하고 조회하는 ORM의 표준이다. 실제 기능은 Hibernate 같은 구현체가 수행한다.
- **영속성 컨텍스트**는 현재 관리 중인 엔티티와 변경 상태를 추적하는 환경이다.
- **EntityManager**는 그 환경을 통해 엔티티를 조회·등록·삭제하는 API다.
- **persist()**는 새 엔티티를 관리 대상으로 등록한다. EntityManager나 영속성 컨텍스트를 만드는 메서드가 아니다.
- **flush()**는 관리 중인 변경을 SQL로 DB에 동기화한다. 트랜잭션을 확정하는 commit과 다르다.
- **영속 엔티티의 필드를 수정하면** 변경 감지를 통해 DB 변경으로 이어질 수 있다. 반영 시점과 최종 확정을 구분해야 한다.
- **수업 테스트는 마지막에 rollback()을 호출한다.** 테스트 중 SQL이 실행되고 검증에 성공해도 그 트랜잭션의 변경은 최종 저장되지 않을 수 있다.

## 2. JPA, ORM, Hibernate, JDBC의 관계

**ORM(Object-Relational Mapping, 객체 관계 매핑)**은 객체 모델과 관계형 DB 모델을 연결하는 기술이다. 클래스와 테이블, 필드와 컬럼, 객체의 참조와 테이블의 외래 키 관계 등을 연결한다. 이 연결을 **매핑(mapping)**이라고 부른다.

**JPA(Java Persistence API)**는 ORM 사용 방법을 정한 자바의 표준 명세다. 현재 표준 이름은 Jakarta Persistence이며, 수업 코드의 패키지는 `jakarta.persistence`다. EntityManager 같은 인터페이스와 @Entity 같은 어노테이션을 제공한다.

**Hibernate**는 이 표준을 구현한 ORM 라이브러리다. JPA 규칙에 맞춰 실제로 객체를 관리하고 SQL을 생성·실행한다. 수업의 의존성은 다음과 같다.

```gradle
implementation 'org.hibernate.orm:hibernate-core:7.2.25.Final'
```

```text
애플리케이션 코드
  → JPA API 호출
  → Hibernate 구현체가 매핑과 객체 상태를 해석
  → JDBC API와 DB 드라이버를 통해 SQL 실행
  → 관계형 DB
```

**쉽게 풀면:** ORM은 객체와 테이블을 연결하는 기술, JPA는 그 기술의 사용 규칙, Hibernate는 그 규칙대로 실제 작업을 하는 구현체다. JDBC는 아래에서 DB와 SQL을 주고받는 데 계속 쓰인다.

**Dialect(방언)**는 DB 제품별 SQL 문법과 기능의 차이를 Hibernate가 다루는 방식이다. MySQL과 다른 DB의 차이를 반영해 SQL을 만들도록 돕는다. 지원되는 DB에서는 JDBC 메타데이터로 적절한 Dialect를 자동 판단할 수도 있어 항상 직접 지정해야 하는 것은 아니다.

근거: [Hibernate 7.2 공식 입문서](https://docs.hibernate.org/orm/7.2/introduction/html_single/).

## 3. 왜 객체와 DB 사이에 문제가 생길까?

객체지향 언어와 관계형 DB는 데이터를 구성하는 방식이 다르다. 이 차이를 **패러다임 불일치**라고 한다. 여기서 패러다임은 데이터를 보고 구성하는 기본 방식이라는 뜻이다.

| 객체 모델 | 관계형 DB 모델 | 필요한 연결 작업 |
|---|---|---|
| 객체와 필드 | 행과 컬럼 | 조회 결과를 객체에 옮기고, 객체 값을 SQL 입력으로 변환 |
| 다른 객체를 참조 | 외래 키로 관계 표현 | 키로 관련 행을 찾고 연관 객체 구성 |
| 상속 구조 | 여러 테이블 또는 구분 컬럼 등 | 상속 구조와 테이블 구조 연결 |
| 객체 참조의 동일성 | 기본 키로 행 식별 | 같은 행을 나타내는 객체가 중복 생성되는 문제 관리 |

직접 JDBC를 쓰면 ResultSet의 컬럼을 읽어 Menu 객체를 만들고 필드를 채우는 작업을 반복하게 된다. 조회 항목이 바뀌면 SQL과 객체 조립 코드도 함께 바꿔야 한다.

JPA는 매핑 정보를 이용해 이 반복 작업을 줄인다. 연관관계도 매핑할 수 있지만, 수업의 초기 Menu 예제는 아직 categoryCode를 숫자 필드로 보관한다. 숫자 필드를 선언했다고 Category 객체와의 연관관계가 자동으로 설정되는 것은 아니다.

**쉽게 풀면:** 자바에서는 객체와 참조를 다루고, DB에서는 행과 키를 다룬다. JPA는 둘을 연결하는 반복 코드를 줄여 주지만 DB 구조나 SQL을 이해할 필요까지 없애 주지는 않는다.

### 장점과 한계

기본 CRUD SQL과 객체 변환 코드를 줄이고, 엔티티 변경 추적과 같은 기능을 사용할 수 있다. 다만 모든 SQL 작성이 없어지는 것은 아니다. 검색에는 JPQL·Criteria 등을 사용하고 필요하면 네이티브 SQL도 사용할 수 있다. 캐시나 SQL 실행 묶음 같은 기능도 사용 방식에 따라 성능에 도움이 된다.

복잡한 조회가 있다고 무조건 MyBatis를 추가해야 하는 것은 아니다. 조회 요구에 맞춰 JPA의 쿼리 기능, 네이티브 SQL, MyBatis 등을 선택한다. MyBatis는 개발자가 작성한 SQL과 객체 결과를 연결하는 SQL 매퍼이고, JPA는 영속 엔티티의 상태까지 관리하는 ORM 표준이다. 매핑과 실행 흐름을 이해하지 못하면 불필요한 쿼리나 성능 저하가 생길 수 있다.

## 4. EntityManagerFactory → EntityManager → 영속성 컨텍스트

| 용어 | 역할 | 쉬운 풀이 |
|---|---|---|
| EntityManagerFactory | 설정과 매핑 정보를 바탕으로 EntityManager 생성 | 엔티티 관리에 필요한 공통 구성을 준비하고 관리 객체를 만드는 객체 |
| EntityManager | 조회·등록·삭제·동기화 API 제공 | 현재 작업에서 JPA 기능을 호출하는 객체 |
| 영속성 컨텍스트(Persistence Context) | 엔티티의 관리 상태와 변경 추적 | 지금 어떤 객체를 관리하고 있고 무엇이 바뀌었는지 유지하는 환경 |
| 엔티티(Entity) | JPA가 매핑을 통해 다루는 객체 | DB의 데이터와 연결해 저장·조회할 수 있도록 정의한 객체 |

메모의 정확한 용어는 **영속성 컨텍스트**다. EntityManager를 “메모리상의 데이터베이스”라고 정의하면 부정확하다. 실제 DB를 대체하는 것이 아니라, 영속성 컨텍스트와 상호작용하는 API다.

### 수업의 생성 코드 읽기

```java
EntityManagerFactory factory =
        Persistence.createEntityManagerFactory("jpatest");

EntityManager entityManager = factory.createEntityManager();
```

첫 줄은 jpatest 영속성 단위의 설정을 사용해 팩토리를 만든다. 영속성 단위는 함께 관리할 엔티티와 DB·트랜잭션 등의 구성을 묶은 단위다. 둘째 줄은 해당 팩토리로 EntityManager를 만든다.

수업의 EntityManagerFactoryGenerator는 static final 필드에 팩토리를 보관하므로 같은 팩토리를 재사용한다. 반면 EntityManagerGenerator.getInstance()는 내부에서 매번 createEntityManager()를 호출한다. **이름이 getInstance여도 매번 같은 EntityManager를 반환하는 코드가 아니다.**

팩토리는 생성 비용이 크므로 보통 영속성 단위별로 재사용한다. 팩토리는 여러 스레드에서 공유할 수 있지만 실제 EntityManager는 여러 스레드가 동시에 사용하도록 공유하지 않는다. 직접 만든 EntityManager는 작업 후 close()로 정리한다.

수업처럼 createEntityManager()로 직접 만든 EntityManager들은 각각 독립된 영속성 컨텍스트를 갖는다. Spring 환경에서는 주입된 EntityManager가 프록시이며 실제 컨텍스트가 트랜잭션 등에 따라 연결될 수 있으므로, 변수나 주입 지점이 다르다는 이유만으로 항상 별도 컨텍스트라고 판단하지는 않는다.

### 설정 파일

수업은 일반 Java 프로젝트에서 `src/main/resources/META-INF/persistence.xml`을 사용하는 표준 부트스트랩 방식이다. 여기에 영속성 단위와 연결 설정 등을 정의한다. JPA 설정에 XML만 가능한 것은 아니며 프로그램 방식의 설정도 있다.

Spring Boot에서는 application.properties나 application.yml과 자동 설정으로 구성을 간편하게 만들 수 있다. YAML 자체가 JPA 기능을 수행하는 것은 아니며, Spring Boot가 설정을 읽어 필요한 객체를 구성한다.

근거: [EntityManagerFactory API](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/EntityManagerFactory.html), [EntityManager API](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/EntityManager.html).

## 5. 엔티티 매핑 어노테이션

수업의 CRUD용 Menu는 다음과 같은 매핑을 사용한다. 아래는 주요 부분을 발췌한 것이다.

```java
@Entity(name = "Section02Menu")
@Table(name = "tbl_menu")
public class Menu {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "menu_code")
    private int menuCode;

    @Column(name = "menu_name")
    private String menuName;

    protected Menu() {}
    // 나머지 필드·생성자·getter·setter 생략
}
```

| 어노테이션 | 의미 |
|---|---|
| @Entity | JPA 엔티티임을 선언. name은 JPQL 등에서 사용하는 엔티티 이름 |
| @Table(name = "tbl_menu") | 매핑할 실제 DB 테이블 이름 지정 |
| @Id | 엔티티 식별자 지정. 일반적으로 테이블의 기본 키와 연결 |
| @Column(name = "menu_name") | 필드와 연결할 DB 컬럼 이름 지정 |
| @GeneratedValue | 식별자 값을 자동 생성하는 방식 지정 |
| GenerationType.IDENTITY | DB의 identity/자동 증가 컬럼을 이용한 식별자 생성 |

**쉽게 풀면:** 이 어노테이션들은 “이 객체의 어떤 값이 어느 테이블·컬럼에 해당하는가”를 알려 주는 설정이다. @Id는 DB를 가져오는 실행 명령이 아니라 각 엔티티를 구분할 식별자 표시다. 엔티티에는 직접 또는 상속을 통해 식별자가 정의되어 있어야 한다.

JPA 엔티티에는 public 또는 protected 기본 생성자가 필요하다. @Entity의 이름과 @Table의 이름은 역할이 다르므로 섞어서 이해하지 않는다.

근거: [Jakarta Persistence — 엔티티·매핑 규칙](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html).

## 6. 트랜잭션, flush, commit, rollback

**트랜잭션(transaction)**은 DB 작업을 하나의 처리 단위로 묶는 것이다. 수업은 EntityTransaction을 사용해 직접 시작하고 되돌리는 resource-local 방식이다.

| 호출 | 역할 | 쉬운 풀이 |
|---|---|---|
| transaction.begin() | 트랜잭션 시작 | 함께 처리할 DB 작업 범위 시작 |
| entityManager.flush() | 관리 중인 변경을 DB와 동기화 | 필요한 INSERT·UPDATE·DELETE SQL 실행 |
| transaction.commit() | 트랜잭션 확정 | 변경을 최종 반영. 아직 flush하지 않은 변경도 반영 후 확정 |
| transaction.rollback() | 트랜잭션 취소 | 해당 트랜잭션의 DB 변경을 되돌림 |

**flush는 commit이 아니다.** flush로 SQL이 실행되어도 트랜잭션은 계속 진행 중일 수 있다. 이후 rollback하면 그 트랜잭션의 변경을 취소할 수 있다. 같은 트랜잭션 안에서는 커밋 전 자신의 변경을 조회할 수 있고, 다른 연결에서 보이는지는 DB의 격리 수준 등에도 달려 있다.

일반적인 설정에서는 커밋 과정에서 flush가 일어나므로 매번 직접 flush를 호출해야 하는 것은 아니다. AUTO 모드에서는 쿼리 결과의 일관성을 위해 필요한 경우 조회 쿼리 전에 자동 flush가 일어날 수도 있다.

**주의해서 읽을 점:** IDENTITY 식별자를 쓰는 수업 예제는 생성된 키를 얻기 위해 persist 시점에 INSERT가 먼저 실행될 수 있다. 모든 INSERT가 반드시 수동 flush 호출까지 기다린다고 외우면 안 된다. SQL 실행 시점과 트랜잭션 확정 시점은 별개다.

rollback 후 Java 객체의 필드 값까지 자동으로 이전 값으로 돌아가는 것은 아니다. DB 변경 취소와 메모리 객체의 값 변경은 구분한다. close()도 commit을 대신하지 않는다.

근거: [EntityTransaction API](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/EntityTransaction.html), [Hibernate의 식별자 생성·동기화 설명](https://docs.hibernate.org/orm/7.2/introduction/html_single/).

## 7. CRUD를 코드로 이해하기

다음 변경 예시는 EntityManager가 준비되어 있고 트랜잭션이 시작된 상황을 전제로 한다.

### 조회: find()

```java
Menu menu = entityManager.find(Menu.class, 1);
```

Menu 타입의 식별자 값이 1인 엔티티를 찾는다. 해당 엔티티가 이미 현재 컨텍스트에 있으면 그 객체를 활용할 수 있다. 없으면 DB 등을 통해 조회하며 조회 대상이 없으면 null을 반환한다.

### 등록: persist()

```java
Menu menu = new Menu("신메뉴", 35000, 4, "Y");
entityManager.persist(menu);
```

new로 객체를 만드는 것과 JPA 관리 대상으로 등록하는 것은 별개다. persist는 새 menu를 영속 상태로 만들고 DB 삽입으로 이어지게 한다. 이것이 EntityManager를 생성한다는 뜻은 아니다.

### 수정: 영속 엔티티 변경 감지

```java
Menu menu = entityManager.find(Menu.class, 1);
menu.setMenuName("변경된 이름");
```

수업 코드처럼 일반적인 변경 추적이 활성화된 영속 엔티티는 필드 값을 바꾸면 flush 시 변경을 감지해 UPDATE로 반영한다. 이를 **변경 감지(dirty checking)**라고 한다. 관리 중인 엔티티를 수정할 때 persist나 merge를 다시 호출할 필요는 없다. 조회 결과가 null인지도 실제 업무 코드에서 처리해야 한다.

**쉽게 풀면:** 현재 관리 중인 객체의 값이 바뀌면 JPA 구현체가 변경을 알아내 DB 수정으로 연결한다. 아무 자바 객체나 setter를 호출했다고 모두 DB가 바뀌는 것은 아니다. 관리 상태, 트랜잭션과 설정이 중요하다.

### 삭제: remove()

```java
Menu menu = entityManager.find(Menu.class, 1);
if (menu != null) {
    entityManager.remove(menu);
}
```

관리 중인 엔티티를 삭제 대상으로 만든다. DB 삭제는 동기화와 트랜잭션 처리에 따라 반영된다. remove를 호출해도 자바 변수가 null로 바뀌거나 메모리 객체가 즉시 없어지는 것은 아니다.

근거: [EntityManager CRUD와 상태 변경](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/EntityManager.html).

## 8. 엔티티 생명주기와 상태 확인

**생명주기**는 객체가 만들어진 뒤 관리되고 분리되거나 삭제 대상으로 바뀌는 상태 흐름이다. 판단 기준은 “지금 해당 영속성 컨텍스트가 이 객체를 어떻게 다루는가”다.

| 상태 | 의미 | 예시 |
|---|---|---|
| 비영속(new/transient) | 새로 만들었지만 아직 관리하지 않는 객체 | new Menu(...) 직후 |
| 영속(managed) | 현재 컨텍스트에서 관리 중인 객체 | persist한 객체, find로 조회한 객체 |
| 준영속(detached) | 관리되던 객체가 현재 컨텍스트와 분리됨 | detach·clear·close로 분리 |
| 삭제(removed) | DB에서 삭제할 대상으로 지정된 객체 | 영속 객체에 remove 호출 |

```text
new → 비영속 → persist → 영속
DB 조회 → find → 영속
영속 → detach / clear / close → 준영속
영속 → remove → 삭제 상태
```

영속 상태라고 해서 이미 INSERT와 COMMIT이 끝났다는 뜻은 아니다. 준영속 객체는 값이 남아 있는 일반 자바 객체로 사용할 수 있지만, 이후의 필드 변경은 해당 컨텍스트의 자동 변경 감지 대상이 아니다.

### contains(): 이 객체를 지금 관리하는가?

```java
boolean managed = entityManager.contains(menu);
```

true이면 이 EntityManager의 컨텍스트가 해당 객체를 관리한다. DB에 같은 기본 키의 행이 존재하는지 확인하는 메서드는 아니다. DB 데이터와 필드 값이 같은 객체를 직접 new로 만들어도 자동으로 관리되지 않는다. removed 상태도 contains는 false이므로 false 하나만으로 준영속인지 삭제 상태인지 모두 판단할 수는 없다.

### detach(): 객체 하나 분리

```java
Menu menu = entityManager.find(Menu.class, 10);
entityManager.detach(menu);
menu.setMenuPrice(menu.getMenuPrice() + 1000);
entityManager.flush();
```

분리한 menu를 수정했으므로 그 가격 변경은 이 컨텍스트의 변경 감지로 반영되지 않는다. detach 자체가 DB 행을 삭제하는 것도 아니다. 분리 전 아직 flush하지 않은 해당 객체의 변경은 이후 동기화 대상에서 빠진다.

### clear(): 관리 대상 전체 분리

clear는 현재 컨텍스트의 관리 엔티티들을 분리한다. DB 테이블을 비우는 명령이 아니다. 아직 flush하지 않은 변경은 사라질 수 있으므로 호출 순서가 중요하다.

수업의 `flush → clear → find`는 먼저 DB로 변경을 보내고, 관리 중인 객체를 분리한 뒤 다시 조회해 DB 쪽 반영을 확인하려는 흐름이다. clear가 이미 flush한 SQL을 되돌리는 것은 아니다. DB 변경 취소는 rollback의 역할이다.

### merge(): 상태를 관리 객체로 복사

```java
Menu managedMenu = entityManager.merge(detachedMenu);
```

merge는 전달한 객체의 상태를 영속 객체에 복사하고 그 영속 객체를 반환한다. detachedMenu 자체를 다시 관리 대상으로 바꾸는 것으로 이해하면 안 된다. 이후 변경은 반환받은 managedMenu를 기준으로 다룬다. 컨텍스트에 대응하는 관리 객체가 있으면 이를 활용할 수 있으므로 항상 새 인스턴스를 만든다고 단정하지도 않는다.

수업 테스트에서는 원본 준영속 객체의 contains는 false, 반환 객체의 contains는 true이며 둘은 다른 참조라는 점을 확인한다.

근거: [Jakarta Persistence 엔티티 연산](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html), [EntityManager의 contains·detach·clear·merge](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/EntityManager.html).

## 9. 같은 데이터와 같은 객체는 다르다

같은 컨텍스트에서 같은 엔티티 타입과 식별자로 조회하면, 이미 관리 중인 동일 객체를 재사용할 수 있다. 단, 중간에 clear·detach 등으로 관리 상태를 끊은 상황은 구분해야 한다.

```java
Menu first = entityManager.find(Menu.class, 3);
Menu second = entityManager.find(Menu.class, 3);
assertSame(first, second);
```

반면 수업처럼 따로 만든 두 EntityManager가 같은 행을 조회하면 서로 다른 객체를 관리한다. 값이 같아도 자바 참조가 같은 것은 아니다.

- **동일성**: 같은 객체를 가리키는가? 객체의 == 또는 assertSame으로 확인한다.
- **동등성**: 비교 기준에 따라 값이 같은가? assertEquals 등을 사용한다. 객체 비교는 equals 구현에 따라 의미가 달라진다.
- **1차 캐시**: 영속성 컨텍스트 안에서 관리 엔티티를 재사용하는 기능을 설명할 때 쓰는 표현이다. 모든 사용자·요청이 공유하는 캐시가 아니다.

**쉽게 풀면:** 같은 메뉴 번호를 나타내더라도 별도로 만든 객체일 수 있다. JPA의 동일성 보장은 관리 범위 안에서 이해해야 하며, find를 호출할 때마다 항상 SELECT가 출력되는 것도 아니다.

## 10. JUnit으로 무엇을 확인하는가?

JUnit은 자바 테스트를 작성하고 실행하는 프레임워크다. 수업 build.gradle은 JUnit 5.10.0과 Jupiter를 사용한다. JUnit 테스트라는 이유만으로 항상 단위 테스트인 것은 아니다. 실제 DB와 연동하는 수업 테스트는 DB 상태와 설정에 영향을 받는다.

| 어노테이션 | 의미 |
|---|---|
| @Test | 테스트 메서드로 등록 |
| @DisplayName | 실행 결과에 표시할 읽기 쉬운 이름 지정 |
| @BeforeEach | 각 테스트 전에 준비 코드 실행 |
| @AfterEach | 각 테스트 후 정리 코드 실행 |

```text
BeforeEach → 첫 번째 테스트 → AfterEach
BeforeEach → 두 번째 테스트 → AfterEach
```

given·when·then은 테스트를 읽기 좋게 나누는 작성 방식이다. JUnit이 강제하는 특별한 실행 문법은 아니다.

- **given(준비)**: 입력 객체, 기존 데이터, 조건 준비
- **when(실행)**: 검증할 동작 호출
- **then(확인)**: 실제 결과가 기대와 맞는지 assertion으로 검사

when이 반드시 DB 전달과 객체 변환만 뜻하는 것은 아니다. 테스트할 동작이 무엇인지에 따라 달라진다. 클래스 이름 끝의 Test나 Tests는 흔한 관례이며 테스트 실행 도구의 검색 설정도 영향을 줄 수 있다.

근거: [JUnit 5.10 사용자 가이드](https://docs.junit.org/5.10.0/user-guide/).

### Assertions를 한국어로 읽기

assertion은 “지금 이 조건이 맞아야 한다”는 검증문이다. 성공하면 보통 다음 줄로 계속 진행하고, 실패하면 오류를 발생시킨다. assert 메서드가 성공 여부를 boolean으로 반환하는 것으로 이해하면 안 된다.

| 검증문 | 통과 조건을 말로 읽으면 |
|---|---|
| assertTrue(condition) | 조건이 참이어야 한다 |
| assertFalse(condition) | 조건이 거짓이어야 한다 |
| assertEquals(expected, actual) | 기대값과 실제 값이 같아야 한다 |
| assertSame(first, second) | 같은 객체를 가리켜야 한다 |
| assertNotSame(first, second) | 서로 다른 객체여야 한다 |
| assertNotNull(value) | 값이 null이면 안 된다 |
| assertNull(value) | 값이 null이어야 한다 |

```java
assertFalse(menuList.isEmpty());
```

isEmpty가 false여야 하므로 **메뉴 목록이 비어 있지 않아야 통과**한다.

```java
assertFalse(entityManager.contains(detachedMenu));
```

contains가 false여야 하므로 **이 객체를 현재 컨텍스트가 관리하지 않아야 통과**한다.

출력문은 사람이 정보를 읽는 용도이며, System.out.println이 실행됐다는 사실만으로 검증한 것은 아니다. 모든 검증과 준비·정리 과정에서 실패가 없어야 테스트가 정상 완료된다. 테스트가 통과했다는 것은 작성한 조건을 만족했다는 뜻이며 애플리케이션의 모든 동작을 보장하는 것은 아니다.

근거: [JUnit Assertions API](https://docs.junit.org/5.10.0/api/org.junit.jupiter.api/org/junit/jupiter/api/Assertions.html).

## 11. 수업 테스트를 순서대로 해석하기

### 공통 준비와 정리

BeforeEach는 새 EntityManager를 얻고 transaction.begin()을 호출한 뒤 테스트 대상 객체를 만든다. AfterEach는 활성 트랜잭션을 rollback하고 EntityManager를 닫는다. JUnit 자체가 알아서 DB를 롤백하는 것이 아니라 수업의 정리 코드가 직접 호출한다.

### 등록 테스트의 흐름

```java
// 준비: 아직 JPA가 관리하지 않는 새 객체
Menu newMenu = new Menu("신메뉴", 35000, 4, "Y");

// 실행
entityManager.persist(newMenu);
entityManager.flush();
int newMenuCode = newMenu.getMenuCode();
entityManager.clear();

// 확인: 같은 트랜잭션 안에서 다시 조회
Menu savedMenu = entityManager.find(Menu.class, newMenuCode);
assertNotNull(savedMenu);
assertEquals("신메뉴", savedMenu.getMenuName());

// 테스트 종료 후 공통 정리: rollback과 close
```

1. persist로 newMenu를 관리 상태로 바꾼다. IDENTITY 전략에서는 이때 INSERT가 먼저 실행될 수 있다.
2. flush로 아직 반영되지 않은 변경을 DB와 동기화한다.
3. clear로 기존 관리 객체를 분리한다.
4. find로 다시 조회해 DB 쪽에 반영된 데이터를 검사한다.
5. 검증이 통과해도 AfterEach가 rollback하므로 이 트랜잭션의 등록은 취소된다.

### 나머지 생명주기 테스트에서 확인하는 것

| 테스트 흐름 | 확인하는 내용 |
|---|---|
| 조회 객체와 같은 값으로 new한 객체 비교 | 값이 같아도 new 객체가 자동으로 관리되지는 않음 |
| 같은 EntityManager에서 같은 키 두 번 조회 | 현재 관리 범위 안의 동일 객체 재사용 |
| 서로 다른 EntityManager에서 같은 키 조회 | 같은 행을 나타내는 서로 다른 객체 |
| detach 후 값 수정·flush·재조회 | 분리된 객체의 변경이 자동 반영되지 않음 |
| merge 후 원본과 반환값 비교 | 원본은 준영속이며 반환 객체가 영속 상태 |
| clear 후 다시 조회 | 이전 참조는 관리 대상에서 빠지고 별도 객체 조회 |
| remove·flush·clear 후 조회 | 같은 트랜잭션 안에서 삭제 결과를 확인 |

### SQL 출력은 이렇게 읽기

- SELECT: DB에서 조회가 실행되었다. 같은 컨텍스트의 반복 find는 추가 SELECT 없이 처리될 수 있다.
- INSERT: 등록 SQL이 실행되었다. IDENTITY 때문에 persist 때 바로 보일 수도 있다.
- UPDATE: 변경이 DB 수정으로 동기화되었다.
- DELETE: 삭제가 DB에 전달되었다.
- SQL 출력만으로 commit 완료를 판단할 수 없다. 이후 commit·rollback 흐름을 함께 봐야 한다.

수업 테스트는 이미 특정 메뉴 번호가 DB에 있다는 조건을 사용한다. 데이터가 없거나 DB 연결 설정이 다르면 다른 결과가 날 수 있다. 여기서 설명한 결과는 소스의 의도와 공식 동작을 해석한 것이며, 테스트를 실제 실행한 결과는 아니다.

## 12. 메모의 질문에 답하기

| 메모의 질문 | 정리한 답 |
|---|---|
| persist로 EntityManager와 컨텍스트를 만드는가? | 먼저 만든 EntityManager에 새 엔티티를 관리 대상으로 등록한다. |
| 영속 상태면 DB 저장이 끝났는가? | 관리 중이라는 뜻이다. SQL 실행과 커밋 완료를 별도로 확인해야 한다. |
| DB와 컨텍스트가 다르면 flush를 사용하는가? | 관리 중인 변경을 DB에 동기화한다. DB의 모든 변경을 메모리로 다시 읽는 동작은 아니다. |
| flush로 commit하는가? | SQL 동기화와 트랜잭션 확정은 다르다. commit은 트랜잭션을 확정한다. |
| 값 수정은 setter만 호출하면 되는가? | 일반적인 영속 엔티티의 변경은 변경 감지로 반영된다. 준영속 객체 수정에는 자동 적용되지 않는다. |
| clear는 DB를 비우는가? | 컨텍스트의 관리 엔티티를 분리한다. 테이블 데이터 삭제가 아니다. |
| contains는 DB에 행이 있는지 확인하는가? | 현재 이 객체를 관리하는지 검사한다. |
| 테스트 성공이면 변경이 DB에 남는가? | 테스트의 트랜잭션 정리에 달려 있다. 수업 코드는 rollback하므로 최종 저장을 취소한다. |

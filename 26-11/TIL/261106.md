# 2026-11-06 TIL — JPA 실습 복습과 Spring Security의 인증 흐름

> `261106.txt`, JPA 7장, Security 1장 소스를 바탕으로 작성했다. 클래스의 역할과 값이 이동하는 순서부터 읽고, 주요 코드를 한 줄씩 풀이했다. 코드가 의도한 동작과 현재 작성된 범위도 구분했다. 소스·공식 문서를 대조한 설명이며 실제 서버나 DB 테스트를 실행한 결과는 아니다.

## 1. 오늘 배운 내용의 두 흐름

첫 번째는 JPA 실습의 마무리다. 생성·수정 시각을 기록하고, 사용자가 입력한 검색 조건을 조합해 조회한다.

두 번째는 Spring Security다. 회원가입 때 비밀번호를 어떻게 저장하고, 요청이 들어왔을 때 누가 요청했는지 확인하고, 어떤 기능까지 허용할지 정한다.

```text
JPA 실습: 저장·수정 이벤트 → 시각 기록
          검색 입력 → 조건식 구성 → Repository 조회

Security: 가입 입력 → 비밀번호 해시 저장
          인증 정보가 있는 요청 → 사용자 조회 → 비밀번호 검사 → 권한 검사
```

두 흐름은 다른 기능이다. JPA가 DB를 다룬다는 이유만으로 사용자의 비밀번호를 자동 검사하는 것은 아니다.

## 2. 생성·수정 시각을 자동으로 기록하기

**Auditing**은 누가 언제 생성·수정했는지 같은 정보를 기록하는 기능이다. 수업은 그중 생성 시각과 수정 시각을 기록한다.

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseTimeEntity {
    @CreatedDate
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    // getter 생략
}
```

| 줄 | 말로 읽기 |
|---|---|
| @MappedSuperclass | 이 부모 클래스의 필드 매핑을 상속받는 엔티티에 포함 |
| @EntityListeners(...) | 엔티티의 저장·수정 이벤트를 처리할 리스너 연결 |
| AuditingEntityListener.class | 사용할 리스너 타입 지정 |
| abstract class BaseTimeEntity | 이 타입을 직접 new로 생성하지 않고 공통 부모로 사용 |
| @CreatedDate | 생성 시각을 기록할 필드 표시 |
| @LastModifiedDate | 마지막 수정 시각을 기록할 필드 표시 |
| LocalDateTime | 날짜와 시각을 나타내는 자바 타입 |

```java
public class PurchaseOrder extends BaseTimeEntity {
    // 주문 엔티티의 필드와 메서드
}
```

위는 상속 부분 발췌다. 실제 PurchaseOrder에는 @Entity 등의 매핑도 있다. PurchaseOrder가 상속하면 시각 필드 매핑도 주문 테이블에 포함된다. BaseTimeEntity만을 위한 별도 엔티티 테이블을 만든다는 뜻은 아니다.

Application에는 다음 설정이 있다.

```java
@EnableJpaAuditing
@SpringBootApplication
public class Application {
    // main 생략
}
```

@EnableJpaAuditing은 auditing 기능을 활성화한다. 필드의 어노테이션, 엔티티 리스너, 기능 활성화가 함께 동작해야 한다. setter를 호출하는 바로 그 순간 모든 시각이 즉시 바뀌는 기능으로 이해하면 안 된다. JPA 저장·수정 이벤트와 flush 시점을 함께 봐야 한다.

**쉽게 풀면:** 생성 시각·수정 시각 필드를 여러 엔티티에 반복 작성하지 않고 부모 클래스에 모은 뒤, 저장·수정 과정에서 값을 채우도록 구성하는 것이다.

근거: [Spring Data JPA Auditing](https://docs.spring.io/spring-data/jpa/reference/auditing.html), [Jakarta Persistence 매핑 규칙](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html).

## 3. JpaSpecificationExecutor — 여러 검색 조건을 조합하기

Specification은 JPA Criteria API로 엔티티의 조회 조건을 표현하는 방식이다. Criteria API는 SQL 문자열을 직접 이어 붙이는 대신 자바 메서드로 조건을 구성하는 API다.

```java
public interface MenuRepository
        extends JpaRepository<Menu, Integer>, JpaSpecificationExecutor<Menu> {
}
```

JpaRepository는 기본 저장·조회·삭제 기능을 제공한다. JpaSpecificationExecutor는 Specification 조건으로 검색하는 기능을 추가한다. Menu는 검색 대상 엔티티 타입이다. 두 인터페이스 상속 문법 자체는 맨 아래 보충 메모에서 설명한다.

```java
menus.findAll(
        MenuSpecifications.search(keyword, minPrice, maxPrice, categoryCode),
        pageable
);
```

이 코드는 검색 조건과 페이지 조건을 Repository에 전달한다. 메뉴 전체를 자바 메모리로 먼저 가져와 if로 걸러 내는 것과 다르다. 만든 조건을 조회 쿼리에 적용한다.

### 조건을 만드는 코드의 재료

| 이름 | 역할 | 쉬운 풀이 |
|---|---|---|
| root | 조회 대상 엔티티의 속성 경로 | 어느 필드의 값을 비교할지 선택 |
| query | 조회 쿼리 전체 구성 | 조회 구조에 관한 설정 대상 |
| cb | CriteriaBuilder | 비교·LIKE·AND 같은 조건을 만드는 API |
| Predicate | JPA Criteria 조건식 타입 | DB 조회에 적용할 참·거짓 조건 |
| List<Predicate> | 조건식 목록 | 입력된 검색 조건들을 모음 |

여기서 Predicate는 `jakarta.persistence.criteria.Predicate`다. 이름이 같아도 java.util.function.Predicate와 동일한 타입은 아니다.

### 이해를 위한 완성 예시

아래는 네 검색 조건을 모두 적용하도록 정리한 예시다. 현재 수업 소스와 다른 부분은 이어서 설명하며, 소스 파일 자체는 수정하지 않았다. escapeLike는 수업에 있는 문자열 처리 메서드를 사용한다.

```java
public static Specification<Menu> search(
        String keyword, Integer minPrice, Integer maxPrice, Integer categoryCode) {
    return (root, query, cb) -> {
        List<Predicate> conditions = new ArrayList<>();

        if (keyword != null && !keyword.isBlank()) {
            String pattern = "%" + escapeLike(keyword) + "%";
            conditions.add(cb.like(root.get("menuName"), pattern, '!'));
        }
        if (minPrice != null) {
            conditions.add(cb.greaterThanOrEqualTo(root.get("menuPrice"), minPrice));
        }
        if (maxPrice != null) {
            conditions.add(cb.lessThanOrEqualTo(root.get("menuPrice"), maxPrice));
        }
        if (categoryCode != null) {
            conditions.add(cb.equal(
                    root.get("category").get("categoryCode"), categoryCode));
        }
        return cb.and(conditions.toArray(new Predicate[0]));
    };
}
```

| 코드 | 하는 일 |
|---|---|
| new ArrayList<>() | 아직 조건이 없는 목록 생성 |
| keyword != null | 검색어가 전달되었는지 검사 |
| !keyword.isBlank() | 빈 문자열·공백만 있는 검색어는 제외 |
| root.get("menuName") | Menu의 menuName 속성 선택 |
| cb.like(..., pattern, '!') | 이름의 부분 일치 조건 생성. !는 이 패턴의 이스케이프 문자 |
| greaterThanOrEqualTo | 가격이 최소 가격 이상이라는 조건 |
| lessThanOrEqualTo | 가격이 최대 가격 이하라는 조건 |
| root.get("category").get("categoryCode") | 연관 카테고리의 번호 속성 선택 |
| cb.equal | 카테고리 번호 일치 조건 생성 |
| conditions.add(...) | 만든 조건을 목록에 추가 |
| toArray(new Predicate[0]) | 조건 목록을 Predicate 배열로 변환 |
| cb.and(...) | 조건들을 모두 만족하도록 AND로 결합 |

조건이 하나도 없으면 이 AND는 참 조건이 되어 별도 필터 없이 조회할 수 있다. `%검색어%`는 검색어를 포함하는 이름을 찾는 패턴이다. escapeLike는 사용자가 입력한 %, _, !가 검색 패턴 문법으로 잘못 해석되지 않도록 처리한다.

**쉽게 풀면:** 값이 들어온 조건만 하나씩 추가하고 마지막에 “이 조건들을 모두 만족하라”로 묶는 것이다. 입력값 유효성 검사와 조회 조건 생성은 서로 다른 일이다.

### 현재 소스에서 바로잡아 읽을 부분

현재 확인한 MenuSpecifications에는 `keyword != null && keyword.isBlank()`가 있다. 이대로라면 일반 검색어가 아니라 공백인 검색어일 때 이름 조건을 추가한다. 의도가 “내용 있는 검색어만 적용”이라면 `!keyword.isBlank()`가 맞다.

최소 가격과 카테고리 조건은 추가되어 있지만 최대 가격 조건은 아직 없다. maxPrice를 매개변수로 받았다고 SQL에도 자동 반영되는 것은 아니다. 위 예시의 lessThanOrEqualTo 같은 조건을 별도로 넣어야 한다.

또 현재 MenuService.search에는 @Transactional이 없고 응답 변환 중 LAZY 카테고리 이름을 읽는다. open-in-view=false인 일반 요청 흐름에서는 관리 범위가 끝난 뒤 지연 로딩 오류가 발생할 수 있다. DTO 변환까지 읽기 전용 서비스 트랜잭션 안에서 처리하는 등 범위를 설계해야 한다. 트랜잭션을 추가하는 것만으로 N+1 문제가 모두 사라지는 것은 아니다.

근거: [Spring Data JPA Specifications](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html).

## 4. Spring Security는 무엇을 확인하는가?

Spring Security는 Spring 기반 애플리케이션의 인증·인가와 여러 보안 기능을 제공하는 보안 프레임워크다. `org.springframework.security...`는 관련 자바 타입들이 있는 패키지다.

| 구분 | 질문 | 예 |
|---|---|---|
| 인증(Authentication) | 요청자가 누구인지 확인했는가? | 아이디와 비밀번호 확인 |
| 인가(Authorization) | 이 요청자가 이 작업을 해도 되는가? | ADMIN 역할만 관리자 API 허용 |

USER로 인증에 성공해도 ADMIN 기능까지 허용되는 것은 아니다. 인증 성공과 권한 확인은 서로 다른 단계다.

처음 읽을 클래스는 SecurityConfig, CustomUserDetailService, UserAccountService다. DB에 회원을 저장하는 과정과 저장된 회원으로 요청을 인증하는 과정을 나눠 보면 된다.

## 5. Security 1장 클래스의 역할

| 타입 | 역할 |
|---|---|
| SecurityBasicApplication | Spring Boot 시작 |
| SecurityConfig | PasswordEncoder·인증 제공자·보안 필터 규칙 구성 |
| UserAccount | DB 회원 엔티티. 아이디·비밀번호 해시·역할·활성 여부 저장 |
| UserRole | USER·ADMIN 역할 종류 |
| UserAccountRepository | 회원 조회·중복 여부 조회·저장 |
| SignupRequest | 회원가입 입력 record |
| UserResponse | 회원가입 등 응답용 record. 비밀번호 제외 |
| UserAccountService | 중복 확인·비밀번호 해시 처리·회원 저장 |
| CustomUserDetailService | DB 회원을 찾아 Security용 UserDetails로 변환 |
| GlobalExceptionHandler | 현재 일부 업무 예외를 HTTP 응답으로 변환 |

### 직접 만든 타입과 프레임워크 타입을 구분하기

| 타입 | 출처 | 역할 |
|---|---|---|
| UserAccount | 수업 코드 | 우리 DB의 회원 표현 |
| UserDetails | Spring Security 인터페이스 | Security가 읽는 아이디·비밀번호·권한·계정 상태 규격 |
| User | org.springframework.security.core.userdetails | UserDetails의 기본 구현 클래스 |
| UserDetailsService | Spring Security 인터페이스 | 아이디로 UserDetails를 가져오는 사용법 정의 |
| DaoAuthenticationProvider | Spring Security 클래스 | 사용자 조회와 비밀번호 검증을 연결해 인증 |
| SecurityFilterChain | Spring Security 인터페이스 | 요청에 적용할 보안 필터와 매칭 구성 |

**쉽게 풀면:** DB의 회원 객체와 Security가 검사할 사용자 정보는 같은 타입일 필요가 없다. DB 회원을 Security가 읽을 형식으로 바꿔 준다. 여기서 User는 수업 엔티티의 별명이 아니라 Spring Security가 제공하는 클래스다.

현재 1장 소스에는 HTTP 요청을 서비스에 연결하는 Controller가 없다. 따라서 api-test.http에 적힌 주소를 호출한다고 회원가입·내 정보·관리자 기능이 모두 이미 구현되어 실행되는 상태로 이해하면 안 된다. 서비스와 보안 구성의 역할을 먼저 읽어야 한다.

## 6. 비밀번호 저장 — PasswordEncoder와 BCrypt

PasswordEncoder는 비밀번호를 단방향으로 변환하고 원래 입력과 저장된 변환 결과가 일치하는지 검사하는 인터페이스다. BCryptPasswordEncoder는 그 인터페이스를 구현한 클래스다.

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

- new BCryptPasswordEncoder(): BCrypt 방식 구현 객체 생성
- return: 그 객체를 반환
- @Bean: 반환 객체를 Spring Bean으로 등록
- 반환 타입 PasswordEncoder: 구체 클래스보다 공통 인터페이스로 사용

### encode와 matches

```java
String storedHash = passwordEncoder.encode(rawPassword);
boolean correct = passwordEncoder.matches(inputPassword, storedHash);
```

encode는 저장할 해시를 만든다. matches는 인증 시 입력 비밀번호가 저장된 해시와 맞는지 검증한다. 해시를 복호화해 원래 비밀번호를 읽는 방식이 아니다.

BCrypt는 salt라는 임의 값을 포함해 처리하므로 같은 비밀번호를 encode해도 결과 문자열이 매번 다를 수 있다. 따라서 `encode(inputPassword).equals(storedHash)`로 비교하지 않는다. matches가 저장된 해시의 정보를 사용해 검사한다.

**쉽게 풀면:** 회원가입 때는 저장용 변환을 하고, 인증 때는 입력한 값이 저장된 값에 대응하는지 검사한다. 저장된 해시를 다시 encode해서 저장하거나, DB에서 꺼낸 해시를 원문 비밀번호로 취급하지 않는다.

### 비밀번호를 응답에 넣지 않는 이유

회원가입 요청에는 비밀번호가 필요하지만 성공 응답에는 필요하지 않다. 수업의 UserResponse는 id·userId·userName·email·role만 포함한다. DB에는 원문 대신 해시를 저장하고, 해시도 일반 응답에 노출하지 않는다.

UserAccount에는 getPassword()가 있으므로 엔티티 전체를 그대로 응답하면 비밀번호 관련 값이 노출될 수 있다. 응답 DTO에서 필요한 값만 선택한다. getPassword가 존재하는 이유는 내부 인증 과정에서 저장된 해시를 읽어야 하기 때문이다.

근거: [Spring Security Password Storage](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html).

## 7. 회원가입 서비스의 실행 순서

수업 UserAccountService.signup의 핵심은 다음과 같다.

```java
@Transactional
public UserResponse signup(SignupRequest request) {
    if (userAccountRepository.existsByUserId(request.userId())) {
        throw new IllegalStateException("이미 사용 중인 아이디입니다.");
    }
    if (userAccountRepository.existsByEmail(request.email())) {
        throw new IllegalStateException("이미 사용 중인 이메일입니다.");
    }

    UserAccount user = new UserAccount(
            request.userId(),
            passwordEncoder.encode(request.password()),
            request.userName(),
            request.email(),
            UserRole.USER
    );
    return UserResponse.from(userAccountRepository.save(user));
}
```

| 코드 | 말로 읽기 |
|---|---|
| SignupRequest request | 회원가입 입력값을 받음 |
| request.userId() | record의 아이디 읽기 메서드 호출 |
| existsByUserId / existsByEmail | 해당 값의 회원이 이미 있는지 조회 |
| throw new IllegalStateException | 중복이면 정상 등록을 중단 |
| encode(request.password()) | 입력한 원문 비밀번호를 저장용 해시로 변환 |
| new UserAccount(...) | 회원 엔티티 생성 |
| UserRole.USER | 신규 가입자의 역할을 서버에서 USER로 지정 |
| repository.save(user) | JPA로 회원 저장 처리 |
| UserResponse.from(...) | 저장 결과에서 응답할 값만 선택 |

**쉽게 풀면:** 입력 확인 → 비밀번호 변환 → 회원 저장 → 비밀번호 없는 응답 구성이다. 중복 사전 조회만으로 동시 가입까지 모두 막을 수는 없으므로 실제 DB의 유일 제약도 함께 중요하다.

회원가입할 때 원문을 해시로 바꾸는 주체는 이 서비스다. 다음 절의 UserDetailsService가 가입할 회원을 만들어 주는 것은 아니다.

## 8. UserDetailsService — 인증에 사용할 회원 조회

```java
@Service
public class CustomUserDetailService implements UserDetailsService {
    private final UserAccountRepository userAccountRepository;

    public CustomUserDetailService(UserAccountRepository userAccountRepository) {
        this.userAccountRepository = userAccountRepository;
    }

    @Override
    public UserDetails loadUserByUsername(String username) {
        UserAccount user = userAccountRepository.findByUserId(username)
                .orElseThrow(() -> new UsernameNotFoundException("회원을 찾을 수 없습니다."));

        return User.withUsername(user.getUserId())
                .password(user.getPassword())
                .roles(user.getRole().name())
                .disabled(!user.isEnabled())
                .build();
    }
}
```

| 줄 | 하는 일 |
|---|---|
| implements UserDetailsService | 사용자 조회 인터페이스를 구현 |
| @Service | Spring이 이 구현 객체를 Bean으로 구성할 수 있게 표시 |
| 생성자 | 필요한 회원 Repository를 전달받음 |
| loadUserByUsername(String username) | 인증에 사용할 아이디를 입력받음 |
| findByUserId(username) | DB에서 그 로그인 아이디로 회원 조회 |
| orElseThrow(...) | 회원이 없으면 인증용 사용자 없음 예외 발생 |
| User.withUsername(...) | Security의 User 객체를 구성하기 시작 |
| password(user.getPassword()) | DB의 비밀번호 해시를 연결. 다시 해시 처리하지 않음 |
| roles(user.getRole().name()) | USER·ADMIN 역할을 Security 권한으로 구성 |
| disabled(!user.isEnabled()) | 비활성 회원이면 비활성 계정으로 표시 |
| build() | 설정한 값으로 UserDetails 구현 객체 완성 |

enabled=true이면 !true는 false이므로 disabled(false), 즉 비활성 상태가 아니다. enabled=false이면 disabled(true)가 된다.

매개변수명이 username이라고 해서 회원의 실제 이름 userName으로 찾는 것은 아니다. 이 구현에서는 username 값을 userId로 조회한다. 역할도 구분해서 읽는다.

**쉽게 풀면:** 입력된 로그인 아이디로 DB 회원을 찾아, Security가 검사할 수 있는 사용자 정보로 바꿔 돌려주는 메서드다. 여기에는 입력 비밀번호 매개변수가 없고 비밀번호 일치 검사도 직접 작성하지 않았다. 그 일은 인증 제공자가 맡는다.

근거: [Spring Security UserDetailsService](https://docs.spring.io/spring-security/reference/7.0/servlet/authentication/passwords/user-details-service.html), [UserDetails](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/user-details.html).

## 9. DaoAuthenticationProvider — 조회와 비밀번호 검사 연결

```java
@Bean
public AuthenticationProvider authenticationProvider(
        UserDetailsService userDetailsService, PasswordEncoder passwordEncoder) {
    DaoAuthenticationProvider provider = new DaoAuthenticationProvider(userDetailsService);
    provider.setPasswordEncoder(passwordEncoder);
    return provider;
}
```

첫 매개변수는 사용자 조회 담당 Bean, 둘째는 비밀번호 검증 담당 Bean이다. DaoAuthenticationProvider를 만들며 조회 담당을 연결하고 setPasswordEncoder로 검증 담당을 연결한다. Spring은 @Bean 메서드 인자에 필요한 Bean을 제공할 수 있다.

**쉽게 풀면:** “누구를 조회할지”와 “비밀번호를 어떻게 확인할지”를 인증 처리에 조합한다. DaoAuthenticationProvider가 직접 UserAccountRepository의 모든 SQL을 작성하는 것은 아니다. 조회는 UserDetailsService 구현을 통해 수행한다.

일반적인 HTTP Basic 인증 흐름은 다음과 같다.

```text
인증 정보가 들어 있는 HTTP 요청
  → 인증 필터가 아이디·비밀번호 추출
  → AuthenticationManager가 적절한 인증 제공자에 위임
  → DaoAuthenticationProvider
  → CustomUserDetailService로 DB 회원 조회
  → UserDetails의 계정 상태 등 확인
  → PasswordEncoder로 입력 비밀번호 검증
  → 성공 시 인증된 Authentication 구성
  → 서버 내부 SecurityContext에 현재 인증 정보 연결
```

AuthenticationManager·Authentication·SecurityContext는 이 단원에서 사용하는 프레임워크 구성 요소다. 각각 인증 처리의 위임, 인증 정보 표현, 현재 보안 정보 보관이라는 역할이다. UserDetails를 만들었다는 이유만으로 인증이 완료되는 것은 아니다.

근거: [DaoAuthenticationProvider 공식 흐름](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/dao-authentication-provider.html).

## 10. SecurityFilterChain — Controller에 가기 전 요청 검사

Servlet 기반 Spring Security는 필터를 사용한다. 필터는 HTTP 요청이 Spring MVC Controller에 도달하기 전후에 처리를 적용할 수 있는 구성 요소다. 필터 체인은 그 처리를 순서대로 연결한다.

```text
HTTP 요청
  → Spring Security 필터들
  → 인증 정보 처리
  → 요청 경로에 필요한 권한 확인
  → 허용되면 Spring MVC → Controller
  → Service → Repository
  → HTTP 응답
```

SecurityFilterChain은 적용할 보안 필터와 요청 매칭을 구성한다. HttpSecurity는 세션 정책·인증 방식·권한 규칙 등을 설정하는 API이고, http.build()가 최종 체인 구성을 만든다.

### 수업 설정을 경로 표기까지 정리해서 읽기

아래는 수업 코드의 경로 앞 /를 보완한 설명용 발췌다. 다른 설정은 그다음에 설명한다.

```java
http.authorizeHttpRequests(authorize -> authorize
        .requestMatchers(HttpMethod.POST, "/api/auth/signup").permitAll()
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .anyRequest().authenticated());
```

| 설정 | 뜻 |
|---|---|
| requestMatchers(POST, "/api/auth/signup") | POST 방식의 이 가입 경로에 해당하는 요청 선택 |
| permitAll() | 이 경로의 인가에서 인증을 필수로 요구하지 않음 |
| requestMatchers("/api/admin/**") | 관리자 하위 경로 선택 |
| hasRole("ADMIN") | 기본 역할 접두사 규칙에 따라 ROLE_ADMIN 권한 확인 |
| anyRequest() | 앞의 규칙에 해당하지 않은 나머지 요청 |
| authenticated() | 인증된 사용자만 허용 |

규칙은 앞에서부터 매칭하므로 구체적인 규칙을 먼저 둔다. permitAll은 DB 검증·입력 검증·다른 보안 필터까지 모두 생략한다는 뜻이 아니다. 또 경로를 허용했다고 해당 Controller 메서드를 자동 생성하지 않는다.

### USER, ADMIN과 ROLE_ 접두사

수업 UserRole에는 USER와 ADMIN이 있다. User.roles("USER")는 기본적으로 ROLE_USER, roles("ADMIN")는 ROLE_ADMIN 권한을 구성한다. 그래서 hasRole("ADMIN")과 대응한다. 이 경우 roles에 이미 ROLE_ADMIN이라는 값을 중복해서 넣지 않는다.

| 요청 규칙 | 미인증 | USER로 인증 | ADMIN으로 인증 |
|---|---|---|---|
| 가입 POST의 permitAll | 인가상 허용 | 인가상 허용 | 인가상 허용 |
| /api/admin/** | 인증 필요 | 권한 부족 | 인가상 허용 |
| 나머지 authenticated | 인증 필요 | 인가상 허용 | 인가상 허용 |

이 표는 보안 규칙의 판단이다. 실제 성공 응답에는 경로 구현과 입력값 등 다른 조건도 필요하다. ADMIN이 USER 역할을 자동으로 상속하는 설정은 없지만, 여기서 나머지 요청은 역할이 아닌 authenticated만 검사하므로 둘 다 통과할 수 있다.

HTTP Basic의 일반적인 API 흐름에서 인증이 없거나 올바르지 않으면 401, 인증은 되었지만 관리자 권한이 부족하면 403을 기대한다. 정확한 응답은 설정한 인증 진입점·접근 거부 처리에도 영향을 받는다.

근거: [Spring Security 필터 구조](https://docs.spring.io/spring-security/reference/servlet/architecture.html), [요청별 인가 규칙](https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html).

## 11. STATELESS와 HTTP Basic을 함께 읽기

```java
.sessionManagement(session ->
        session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
.httpBasic(Customizer.withDefaults())
```

STATELESS는 Spring Security가 HttpSession을 만들거나 세션에서 SecurityContext를 가져와 인증 상태를 유지하지 않는 정책이다. 애플리케이션의 다른 코드가 어떠한 세션도 절대 만들 수 없다는 뜻으로 일반화하지 않는다.

HTTP Basic은 요청의 Authorization 헤더에 아이디와 비밀번호를 담아 인증하는 방식이다. 일반적인 전송 형식은 다음과 같다.

```http
Authorization: Basic <아이디:비밀번호를 Base64로 표현한 값>
```

Base64는 표현을 바꾸는 인코딩이며 비밀을 숨기는 암호화가 아니다. 실제 네트워크 통신에서는 HTTPS로 보호해야 한다. DB의 BCrypt 해시와 HTTP Basic 헤더의 Base64는 서로 다른 목적이다.

**쉽게 풀면:** 이 수업의 1장은 세션에 로그인 상태를 저장해 다음 요청에서 재사용하는 방식이 아니라 요청에 담긴 인증 정보로 사용자를 확인하는 구조다. STATELESS라고 자동으로 JWT를 사용하거나 JWT가 발급되는 것은 아니다. JWT 단원은 별도다.

api-test.http의 Basic 아이디 비밀번호 형태는 이를 지원하는 IDE HTTP 클라이언트의 입력 형식으로 읽어야 한다. 일반 HTTP 헤더의 실제 전송 표현은 위와 같은 Basic과 Base64 값의 조합이다.

### csrf(disable)는 STATELESS의 자동 결론이 아니다

수업 설정에는 `http.csrf(AbstractHttpConfigurer::disable)`가 있다. CSRF 보호를 끄는 설정이다. CSRF는 브라우저가 자동으로 보내는 인증 정보 등을 이용해 원하지 않은 요청을 실행시키는 공격을 말한다.

세션을 사용하지 않는다는 이유만으로 CSRF 위험이 자동으로 없어지지는 않는다. 브라우저의 HTTP Basic 인증도 자동 인증 정보 전송 때문에 영향을 받을 수 있다. 따라서 이 설정을 “STATELESS면 항상 CSRF를 꺼야 한다”로 외우면 안 된다. 인증 정보 전송 방식과 클라이언트 사용 환경을 보고 결정해야 한다.

근거: [SessionCreationPolicy](https://docs.spring.io/spring-security/reference/api/java/org/springframework/security/config/http/SessionCreationPolicy.html), [HTTP Basic](https://docs.spring.io/spring-security/reference/servlet/authentication/passwords/basic.html), [Spring Security CSRF 설명](https://docs.spring.io/spring-security/reference/features/exploits/csrf.html).

## 12. 오늘의 두 과정을 말로 다시 연결하기

### 회원가입 처리

```text
가입 JSON → 요청 DTO → 가입 서비스
  → 중복 확인 → 원문 비밀번호 encode
  → UserAccount 저장 → 비밀번호 없는 UserResponse
```

Controller가 구현되어 요청 DTO를 서비스에 전달해야 실제 HTTP 가입 기능으로 연결된다. permitAll과 signup 서비스만으로 URL 처리가 완성되지는 않는다.

### 보호된 API 요청

```text
요청의 Basic 인증 정보
  → 인증 필터·인증 관리자
  → DaoAuthenticationProvider
  → UserDetailsService로 DB 회원 조회
  → 저장 해시와 입력 비밀번호 검증
  → 인증 정보 구성
  → requestMatchers의 역할·인증 규칙 검사
  → 허용되면 실제 Controller 실행
```

클래스 이름을 볼 때는 “입력값을 받는가, DB를 조회하는가, 비밀번호를 검사하는가, 권한을 정하는가”를 먼저 구분한다. 생성한 UserDetails를 사용자에게 그대로 JSON 응답으로 보내는 과정은 아니다.

## 13. 본문 흐름과 별도로 모은 메모

### 인터페이스는 여러 개 상속할 수 있다

```java
public interface MenuRepository
        extends JpaRepository<Menu, Integer>, JpaSpecificationExecutor<Menu> {
}
```

MenuRepository는 인터페이스이므로 다른 인터페이스 둘을 extends할 수 있다. 자바 클래스가 두 부모 클래스를 extends하는 것은 허용되지 않는다. 클래스는 하나의 클래스를 상속하면서 여러 인터페이스를 implements할 수 있다.

```java
class Example extends OneParent implements FirstRule, SecondRule {
    // 필요한 구현
}
```

위는 타입 이름을 임의로 쓴 문법 예시이며 실제 수업 타입은 아니다. interface가 interface를 확장하면 extends, class가 interface 규격을 구현하면 implements를 사용한다.

**쉽게 풀면:** 여러 인터페이스의 기능 규격을 함께 갖는 것과 여러 부모 클래스의 상태·구현을 동시에 상속하는 것은 다르다.

근거: [Oracle — 자바의 다중 타입 상속](https://docs.oracle.com/javase/tutorial/java/IandI/multipleinheritance.html).

### 현재 Security 1장 소스를 그대로 외우면 안 되는 부분

**1. requestMatchers 경로의 앞 / 누락**

현재 파일에는 `"api/auth/signup"`, `"api/admin/**"`로 적혀 있다. Spring Security 7의 Java 설정은 context root를 제외한 절대 요청 경로 형식을 요구한다. 설명 예시처럼 `"/api/auth/signup"`, `"/api/admin/**"`로 작성해야 한다. 경로 자체의 잘못된 표기는 단순한 권한 조건 문제가 아니라 체인 구성 오류로 이어질 수 있다.

근거: [Spring Security 7 경로 매칭 변경](https://docs.spring.io/spring-security/reference/6.5/migration-7/web.html).

**2. 현재 폴더에 Controller 구현 없음**

현재 1장에 있는 것은 서비스·Repository·엔티티·DTO·보안 구성 등이다. api-test.http의 `/api/auth/signup`, `/api/users/me`, `/api/admin/dashboard`를 실제로 처리할 Controller는 이 폴더에서 확인되지 않는다. 예제 요청 파일이 존재한다고 그 기능이 모두 구현되었다는 뜻은 아니다.

**3. 중복 가입 예외와 예외 처리 타입 불일치**

UserAccountService는 중복이면 IllegalStateException을 던지지만, 현재 GlobalExceptionHandler는 IllegalArgumentException만 잡아 409로 바꾼다. 서로 다른 타입이므로 이 처리기로 중복 예외가 자동 변환되지 않는다. 따라서 현재 소스만으로 “중복이면 409”가 보장된다고 설명하면 틀린다.

중복 회원용 예외를 별도로 정의하고 그 타입을 409로 처리하거나, 서비스와 처리기의 타입을 일치시키도록 설계해야 한다. 임의의 IllegalStateException 전체를 무조건 중복 오류로 간주하는 방식보다는 의미가 명확한 업무 예외를 쓰는 것이 읽기 쉽다.

위 내용은 현재 파일을 대조해 확인한 사항이다. 이 정리를 만들면서 실제 수업 소스는 수정하지 않았다.

### 메서드 호출 모양 복습

| 표현 | 읽는 방법 |
|---|---|
| user.getRole().name() | 회원 역할을 얻고 enum 이름 문자열을 읽음 |
| !user.isEnabled() | 활성 여부의 참·거짓을 반대로 바꿈 |
| User.withUsername(...).password(...).build() | 사용자 정보 구성을 단계적으로 연결한 뒤 객체 완성 |
| Customizer.withDefaults() | 해당 설정의 기본 구성을 사용하도록 지정 |
| session -> session.sessionCreationPolicy(...) | 전달받은 session 설정 객체에 정책을 적용하는 람다 |
| AuditingEntityListener.class | 그 클래스의 타입 정보를 전달 |

### 먼저 복습할 순서

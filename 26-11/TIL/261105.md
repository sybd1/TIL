# 2026-11-05 TIL — 네이티브 쿼리와 JPA 실습을 처음부터 읽기

> 어제 메모와 `chap06-native-query`, `chap07-practical-jpa` 소스를 대조한 학습 정리다. 먼저 클래스가 왜 나뉘는지 이해하고, 실제 코드의 실행 순서와 테스트가 확인하는 내용을 따라간다. 아래 숫자·JSON은 설명을 위한 예시이며 실제 DB 실행 결과가 아니다. 코드 발췌는 import와 일부 메서드를 생략했다.

## 1. 오늘은 두 가지 작업을 배웠다

첫 번째는 **이미 저장된 데이터를 SQL로 계산해 조회하는 일**이다. 카테고리마다 메뉴가 몇 개인지 세거나, 메뉴 가격 순위를 계산한다. 이것이 6장의 네이티브 쿼리 예제다.

두 번째는 **여러 DB 작업을 언제 확정하고 언제 취소할지, 주문과 주문 항목을 어떻게 함께 관리할지 확인하는 일**이다. 이것이 7장의 트랜잭션·주문 생명주기 예제다.

두 장의 MenuService나 MenuRepository는 이름이 같아도 서로 다른 프로젝트·패키지에 있는 타입이다. 하나의 거대한 실행 순서로 섞어 읽지 않는다.

읽는 순서는 다음과 같다.

```text
자바 코드의 기본 표현
  → 클래스별 역할
  → SQL 조회 결과가 JSON이 되는 과정
  → 트랜잭션과 예외
  → 다섯 가지 트랜잭션 테스트
  → 주문·주문 항목 저장과 삭제
```

## 2. 한 줄을 읽기 전에 알아둘 자바 표현

### 클래스, 객체, 변수, 메서드

**클래스**는 데이터와 동작을 정의한 자바 타입이다. **객체**는 그 클래스로 실제 만든 값이다. **변수**는 그 값이나 객체의 참조를 이름으로 다루게 한다. **메서드**는 이름을 붙여 실행할 수 있는 동작이다.

```java
PurchaseOrder order = new PurchaseOrder(customer);
```

| 코드 조각 | 말로 읽기 |
|---|---|
| PurchaseOrder | 이 변수가 다룰 타입 |
| order | 변수 이름 |
| new PurchaseOrder(customer) | customer를 생성자에 전달해 새 주문 객체 생성 |
| = | 오른쪽 결과를 왼쪽 변수에 대입 |
| ; | 문장 끝 |

**생성자**는 new로 객체를 만들 때 필요한 초기 값을 설정하는 코드다. new로 만들었다고 자동으로 DB에 저장되는 것은 아니다.

```java
orders.saveAndFlush(order);
```

여기서는 orders가 가리키는 객체의 saveAndFlush 메서드를 호출하고, order 객체를 인자로 전달한다. 괄호 안의 값이 메서드에 전달하는 **인자**다. 메서드 선언에서 그 값을 받을 이름이 **매개변수**다.

### 같은 orders라는 이름도 위치에 따라 다르다

| 위치 | orders의 실제 타입 | 호출 예시 |
|---|---|---|
| PracticeController | OrderService | orders.create(customer) |
| TransactionTests가 상속받은 FixtureSupport | OrderService | orders.failRuntime(customer) |
| OrderService | OrderRepository | orders.saveAndFlush(order) |

변수 이름만 보고 역할을 판단하면 헷갈린다. **그 변수를 선언한 줄의 타입**을 먼저 본다.

### interface와 어노테이션

**인터페이스**는 제공할 메서드의 형식을 선언하는 타입이다. 수업 Repository는 인터페이스이며 Spring Data가 구현 객체를 구성한다. 조회용 프로젝션 인터페이스도 Spring Data가 결과를 읽을 구현 객체를 만든다.

**어노테이션**은 `@Service`, `@Transactional`처럼 코드에 붙이는 메타 정보다. Spring·JPA 등이 이를 읽어 필요한 처리를 적용한다. 모든 어노테이션이 같은 일을 하거나, 붙인 줄에서 곧바로 DB 작업을 실행하는 것은 아니다.

`private final OrderRepository orders;`는 이 클래스 내부에서 사용할 Repository 참조를 보관하는 필드다. final은 그 필드에 다른 참조를 다시 대입하지 못하게 한다. Repository의 모든 내부 동작을 금지하는 뜻은 아니다. 생성자에서 이 필드를 받으면 Spring이 필요한 Bean을 연결해 준다.

`return`은 메서드의 결과를 호출한 곳으로 돌려준다. `void`는 돌려주는 결과값이 없다는 뜻이다. `this.customer = customer`의 왼쪽 this.customer는 현재 객체의 필드이고, 오른쪽 customer는 전달받은 매개변수다.

## 3. 클래스가 많아 보일 때 읽을 역할표

### 공통 역할부터 구분

| 종류 | 하는 일 | 수업의 예 |
|---|---|---|
| Controller | HTTP 입력을 받고 서비스를 호출해 HTTP 응답 연결 | PracticeController |
| Service | 처리 순서·업무 규칙·트랜잭션 범위 결정 | OrderService |
| Repository | 엔티티 저장·조회·삭제 또는 쿼리 실행 | OrderRepository |
| Entity | DB와 연결되는 데이터와 변경 동작 | PurchaseOrder, OrderLine |
| DTO·record | 요청·응답으로 전달할 값 구성 | CustomerRequest, OrderResponse |
| Projection | 조회 결과의 일부 값을 읽을 형식 | CategoryMenuCountView |
| ExceptionHandler | 예외를 HTTP 오류 응답으로 변환 | GlobalExceptionHandler |
| Test | 실행 결과가 예상 조건과 맞는지 검사 | TransactionTests |

Controller가 JSON을 객체로 바꾸는 모든 코드를 직접 작성하는 것은 아니다. Spring의 메시지 변환기가 요청 본문을 변환한 뒤 Controller 인자로 제공한다. Service도 DTO 변환만 하는 곳이 아니다.

DTO(Data Transfer Object)는 전달할 데이터를 모아 둔 객체다. 엔티티는 DB 저장 구조와 연결된 객체이고, DTO는 요청이나 응답에 필요한 값들을 전달하는 데 사용한다. DTO를 만들었다는 이유만으로 DB에 자동 저장되지는 않는다.

## 4. 네이티브 쿼리 — SQL을 그대로 선언하기

이전 JPQL은 Menu·menuName 같은 엔티티와 속성 이름을 사용했다. 네이티브 SQL은 tbl_menu·menu_name 같은 실제 테이블·컬럼 이름을 사용한다.

```java
@Query(value = "SELECT menu_code FROM tbl_menu", nativeQuery = true)
```

```java
@NativeQuery(value = "SELECT menu_code FROM tbl_menu")
```

위는 어노테이션의 의미를 보여 주는 발췌다. 메서드의 반환 타입도 실제 SQL 결과에 맞게 선언해야 한다. @NativeQuery는 @Query(nativeQuery=true)를 간편하게 선언하는 합성 어노테이션이며 결과 매핑 관련 추가 속성도 있다. 모든 속성까지 완전히 동일한 이름인 것은 아니다.

자바의 `""" ... """`는 여러 줄 문자열을 적는 **텍스트 블록**이다. 그 안의 SQL을 여러 줄로 편하게 적는 자바 문법이지 별도의 SQL 명령은 아니다.

근거: [Spring Data @NativeQuery](https://docs.spring.io/spring-data/jpa/docs/current/api/org/springframework/data/jpa/repository/NativeQuery.html).

### 카테고리마다 메뉴가 몇 개인지 세는 SQL

수업의 findCategoryMenuCounts는 다음 SQL을 사용한다.

```sql
SELECT c.category_code AS categoryCode,
       c.category_name AS categoryName,
       COUNT(m.menu_code) AS menuCount
FROM tbl_category c
LEFT JOIN tbl_menu m ON m.category_code = c.category_code
GROUP BY c.category_code, c.category_name
ORDER BY menuCount DESC, c.category_code
```

| SQL 줄 | 하는 일 |
|---|---|
| FROM tbl_category c | 카테고리 테이블을 기준으로 읽고 c라는 짧은 이름 사용 |
| LEFT JOIN tbl_menu m | 일치하는 메뉴를 연결하며 메뉴 없는 카테고리도 유지 |
| ON m.category_code = c.category_code | 카테고리 번호가 같은 행끼리 연결 |
| GROUP BY ... | 카테고리별로 묶어 계산 |
| COUNT(m.menu_code) | 연결된 메뉴 번호가 NULL이 아닌 개수 계산 |
| AS menuCount | 계산 결과 컬럼 이름을 menuCount로 지정 |
| ORDER BY menuCount DESC | 메뉴 개수가 많은 순서로 정렬 |
| , c.category_code | 개수가 같으면 카테고리 번호 순서로 정렬 |

LEFT JOIN에서 메뉴가 없으면 메뉴 쪽 값이 NULL이다. COUNT(m.menu_code)는 이를 세지 않으므로 메뉴 수 0을 얻는다. COUNT(*)로 바꾸면 조인 결과 행 자체를 세므로 같은 의미가 아니다.

**쉽게 풀면:** 카테고리 목록을 기준으로 연결된 메뉴 수를 세어 결과를 만든다. SELECT에 쓴 순서와 DB가 논리적으로 행을 묶어 처리하는 순서는 구분해서 읽는다.

근거: [MySQL COUNT 함수](https://dev.mysql.com/doc/refman/8.0/en/aggregate-functions.html).

### SQL 결과를 인터페이스로 읽는 이유

```java
public interface CategoryMenuCountView {
    int getCategoryCode();
    String getCategoryName();
    long getMenuCount();
}
```

```java
List<CategoryMenuCountView> findCategoryMenuCounts();
```

프로젝션은 조회 결과를 필요한 값 중심의 형식으로 받는 방식이다. 이 인터페이스에는 DB에 저장할 전체 엔티티 대신 결과를 읽는 메서드만 있다.

| SQL 결과 이름 | 자바 속성 이름 | 읽는 메서드 |
|---|---|---|
| categoryCode | categoryCode | getCategoryCode() |
| categoryName | categoryName | getCategoryName() |
| menuCount | menuCount | getMenuCount() |

AS 뒤의 별칭은 getMenuCount라는 메서드 이름 전체가 아니라, getter가 나타내는 속성 menuCount와 맞춘다. 숫자 반환 타입도 결과에 맞아야 한다. COUNT처럼 개수가 커질 수 있는 값은 수업에서 long으로 받는다.

인터페이스 그 자체를 new로 만들어 값을 넣는 것이 아니다. Spring Data가 조회 결과를 읽을 수 있는 구현 객체, 즉 프로젝션 프록시를 구성한다. List는 그 객체 여러 개를 담는 목록이다.

**쉽게 풀면:** DB 조회 결과의 각 행을 정해진 메서드로 읽을 수 있게 한 것이다. getter는 결과값을 읽는다. 검색 조건을 걸거나 WHERE를 추가하는 동작이 아니다.

근거: [Spring Data JPA 프로젝션](https://docs.spring.io/spring-data/jpa/reference/repositories/projections.html).

### List가 JSON 배열이 되는 전체 흐름

```text
GET /api/v1/menus/reports/category-menu-counts
  → MenuController.findCategoryMenuCounts()
  → MenuService.findCategoryMenuCounts()
  → MenuRepository.findCategoryMenuCounts()
  → DB에서 집계 SQL 실행
  → 결과 행별 CategoryMenuCountView 구현 객체
  → List<CategoryMenuCountView>
  → ResponseEntity.ok(...)
  → Jackson이 JSON 본문 생성
```

```json
[
  {"categoryCode":4,"categoryName":"음료","menuCount":3},
  {"categoryCode":5,"categoryName":"기타","menuCount":0}
]
```

이는 예시 결과다. 바깥 List가 JSON 배열이 되고, 그 안의 프로젝션 객체 하나가 JSON 객체가 된다. Jackson은 여기서 getter를 통해 속성 값을 읽는다. 인터페이스 하나가 배열인 것이 아니다.

### 조건값 바인딩

다음은 사용법을 설명하기 위한 추가 예시다. 원본 집계 메서드에는 이 조건이 없다.

```java
@Query(value = "SELECT * FROM tbl_menu WHERE menu_price >= :minPrice", nativeQuery = true)
List<Menu> findNativeByMinimumPrice(@Param("minPrice") int minPrice);
```

:minPrice는 값이 들어갈 자리이며 @Param이 실제 인자를 연결한다. 20000을 전달하면 20,000원 이상인 메뉴를 조회한다. 이 방식은 값 바인딩이며 테이블명이나 SQL 문법 조각을 임의로 바꾸는 기능이 아니다.

## 5. RANK() OVER — 가격 순위 붙이기

수업 쿼리의 핵심은 다음 두 정렬 기준이다.

```sql
RANK() OVER (ORDER BY m.menu_price DESC) AS priceRank
```

```sql
ORDER BY priceRank, m.menu_code
```

첫 번째 ORDER BY는 **순위를 계산하는 기준**, 마지막 ORDER BY는 **결과 행을 반환할 순서**다. RANK는 같은 가격에 같은 순위를 주고 다음 순위에 빈 번호가 생길 수 있다.

| 가격 | 계산된 RANK |
|---|---|
| 10,000 | 1 |
| 8,000 | 2 |
| 8,000 | 2 |
| 6,000 | 4 |

마지막 menu_code 정렬은 같은 순위끼리 보여 줄 순서를 정한다. RANK 내부에 menu_code까지 넣으면 순위 계산의 동률 기준 자체가 달라질 수 있다.

MySQL 8.0은 RANK 같은 윈도 함수를 지원한다. 윈도 함수는 행들을 기준에 따라 살펴보며 순위 같은 값을 계산하되 GROUP BY처럼 결과를 한 행으로 묶어 줄이지는 않는다. 수업에서는 MenuPriceRankView의 getPriceRank로 순위를 읽는다.

요청 주소는 `GET /api/v1/menus/reports/price-ranks`다.

근거: [MySQL 윈도 함수와 RANK](https://dev.mysql.com/doc/refman/8.0/en/window-function-descriptions.html).

| flush | 관리 중인 변경을 SQL로 DB에 동기화 |
| commit | 해당 트랜잭션을 확정 |
| rollback | 해당 트랜잭션의 DB 변경 취소 |

```java
orders.saveAndFlush(order);
```

saveAndFlush는 저장 처리와 flush를 함께 한다. 현재 컨텍스트의 다른 대기 변경도 flush될 수 있다. **이 메서드를 호출한 줄에서 서비스 전체 트랜잭션까지 반드시 커밋되는 것은 아니다.**

서비스 트랜잭션이 이미 있으면 Repository는 보통 그 트랜잭션에 참여한다. 서비스 트랜잭션이 없고 다른 바깥 트랜잭션도 없다면, 기본 저장소 메서드의 트랜잭션이 시작되고 정상 종료 시 커밋될 수 있다. 어느 트랜잭션 범위에서 호출했는지를 함께 봐야 한다.

### 프록시는 여기서 어떤 일을 하는가?

프록시는 실제 서비스 호출 앞뒤에 부가 처리를 적용하는 객체다. 일반적인 Spring 트랜잭션 방식에서는 다음 순서를 따른다.

```text
외부 호출
  → 서비스 트랜잭션 프록시
  → 트랜잭션 시작 또는 기존 트랜잭션 참여
  → 실제 서비스 메서드 실행
  → 정상 반환인지 예외인지 확인
  → 규칙에 따라 commit 또는 rollback
  → 호출한 쪽으로 결과 또는 예외 전달
```

**쉽게 풀면:** 서비스 메서드의 앞뒤에서 Spring이 트랜잭션 처리를 적용한다. 메모의 정확한 용어는 트랜잭션이며, @Transactional을 붙인 모든 내부 호출에 무조건 별도 트랜잭션이 생기는 것은 아니다.

근거: [Repository 트랜잭션](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html), [saveAndFlush API](https://docs.spring.io/spring-data/jpa/docs/current/api/org/springframework/data/jpa/repository/JpaRepository.html), [@Transactional과 프록시](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).

## 7. 예외와 테스트를 먼저 말로 읽기

**예외(exception)**는 실행 중 문제가 발생했음을 호출한 쪽으로 알리는 방식이다. throw는 예외를 발생시키고, catch는 전달된 예외를 잡아 처리한다. 잡지 않으면 위쪽 호출로 전달된다.

```java
throw new IllegalStateException("저장 후 실패");
```

“이 지점에서 정상 흐름을 멈추고, 저장 후 실패라는 문제를 알린다”는 뜻이다. 이 다음의 일반적인 문장은 실행하지 않고 예외 처리 흐름으로 이동한다.

수업은 실패 상황을 배우려고 일부러 예외를 만든다. IllegalStateException은 RuntimeException 계열이다. IOException은 checked exception이다. 기본 Spring 롤백 규칙은 RuntimeException과 Error에는 롤백, checked exception에는 자동 롤백하지 않는 방식이다. 설정으로 바꿀 수 있다.

### 테스트의 assertThrows는 실패가 발생해야 성공한다

```java
assertThrows(IllegalStateException.class,
        () -> orders.failRuntime(prefix + "실패 주문"));
assertEquals(0, ownOrderCount());
```

| 코드 | 말로 읽기 |
|---|---|
| IllegalStateException.class | 이 타입의 예외를 기대 |
| () -> orders.failRuntime(...) | 나중에 실행할 동작을 전달하는 람다 |
| assertThrows(...) | 실제로 그 예외 또는 하위 타입이 발생하는지 검사 |
| assertEquals(0, ownOrderCount()) | 이번 테스트의 주문 수가 0인지 검사 |

예외를 일부러 발생시키는 테스트이므로 예외가 나왔다고 테스트 실패인 것은 아니다. 기대한 예외가 없거나 타입이 맞지 않으면 검증에 실패한다. 이후 DB 결과도 따로 검사한다.

테스트 쪽 assertThrows가 예외를 잡을 때는 서비스 프록시가 이미 예외를 보고 트랜잭션 처리를 결정한 뒤다. 서비스 안에서 예외를 잡는 것과 시점이 다르다.

### FixtureSupport는 왜 있는가?

FixtureSupport는 테스트가 반복해서 쓸 준비·정리 코드를 모은 부모 테스트 클래스다. @SpringBootTest로 Spring 환경을 띄우고 @Autowired로 서비스·Repository 등을 연결한다. 각 테스트는 extends FixtureSupport로 이를 상속한다.

- BeforeEach: 고유한 prefix 문자열을 만들고, 기존 카테고리를 사용해 테스트 메뉴 3개 준비
- ownOrderCount: customer가 prefix로 시작하는 주문 수만 계산
- AfterEach: 이번 테스트가 만든 주문과 메뉴만 삭제

prefix는 기존 데이터와 이번 테스트 데이터를 구분하는 표시다. 테스트 전체에 @Transactional을 붙이지 않았으므로 각 서비스가 실제로 커밋·롤백한 결과를 다음 조회로 확인한다. 정리 코드는 커밋된 테스트 데이터를 마지막에 다시 지우는 동작이지, 앞의 서비스 커밋이 없었다는 뜻이 아니다.

근거: [Spring 기본 롤백 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html), [JUnit Assertions](https://docs.junit.org/5.10.0/api/org.junit.jupiter.api/org/junit/jupiter/api/Assertions.html).

## 8. TransactionTests의 다섯 실험

아래는 저장과 flush가 정상 완료되고 다른 외부 트랜잭션이 없는 수업 조건에서 각 테스트가 기대하는 결과다. 실제 테스트를 실행한 결과를 보고한 것은 아니다.

| 테스트 | 서비스 동작 | 기대 주문 수 | 확인하는 규칙 |
|---|---|---:|---|
| runtimeRollback | 저장 후 RuntimeException 발생 | 0 | 기본 롤백 |
| checkedExceptionCommitsByDefault | 저장 후 IOException 발생 | 1 | checked exception은 기본적으로 커밋 가능 |
| rollbackForCheckedException | IOException을 rollbackFor로 지정 | 0 | 지정한 checked exception도 롤백 |
| locallyCaughtBusinessExceptionDoesNotTriggerRollback | 직접 던진 예외를 서비스 내부에서 catch | 1 | 프록시가 정상 반환을 보면 커밋 가능 |
| selfInvocationBypassesServiceTransaction | 같은 객체 내부에서 트랜잭션 메서드 직접 호출 | 1 | 서비스 프록시를 거치지 않아 저장소 트랜잭션만 확정 |

### ① RuntimeException: 저장했어도 취소

```java
@Transactional
public void failRuntime(String customer) {
    orders.saveAndFlush(new PurchaseOrder(customer));
    throw new IllegalStateException("저장 후 실패");
}
```

프록시가 트랜잭션을 시작한다. 저장소는 그 트랜잭션에 참여해 INSERT를 실행할 수 있다. 그 후 예외가 서비스 밖으로 전달된다. 프록시가 기본 롤백 대상이라고 판단해 취소하므로, 이후 조회한 테스트 주문 수는 0이어야 한다.

### ② checked exception: 예외가 있어도 기본 규칙은 커밋

```java
@Transactional
public void failCheckedDefault(String customer) throws IOException {
    orders.saveAndFlush(new PurchaseOrder(customer));
    throw new IOException("체크 예외 기본 규칙 확인");
}
```

throws IOException은 이 메서드가 해당 예외를 전달할 수 있음을 선언한다. 실제 발생은 throw가 한다. 기본 롤백 대상이 아니므로, 다른 문제가 없다면 프록시는 DB 변경을 커밋하고 IOException은 호출자에게 전달한다. 테스트는 예외 발생과 주문 1건 존재를 동시에 기대한다.

### ③ rollbackFor: checked exception도 취소하도록 지정

```java
@Transactional(rollbackFor = IOException.class)
public void failCheckedRollback(String customer) throws IOException {
    orders.saveAndFlush(new PurchaseOrder(customer));
    throw new IOException("체크 예외도 롤백");
}
```

두 번째 예시와 예외 종류는 같지만 롤백 규칙이 다르다. 그래서 주문 수 0을 기대한다. 예외가 발생했다는 사실 하나만으로 결과를 판단하면 안 된다.

### ④ 서비스 내부 catch: 프록시가 예외를 보지 못함

```java
@Transactional
public void swallowFailure(String customer) {
    try {
        orders.saveAndFlush(new PurchaseOrder(customer));
        throw new IllegalStateException("업무 단계 실패");
    } catch (IllegalStateException e) {
        // 예외를 다시 던지지 않음
    }
}
```

수업은 성공한 저장 뒤에 직접 만든 예외를 같은 메서드 안에서 잡는다. 프록시까지 전달되지 않으므로 프록시는 정상 반환으로 처리하고 커밋할 수 있다.

**여기서 일반화하면 안 되는 점:** DB 저장 자체가 실패했거나 내부의 다른 트랜잭션 참여 코드가 rollback-only로 표시했다면, 예외를 잡아도 커밋되지 않을 수 있다. 수업의 결과는 직접 던진 업무 예외를 내부에서 잡는 특정 상황이다.

### ⑤ self-invocation: 같은 객체 내부 호출

```java
public void selfInvocation(String customer) {
    failRuntime(customer);
}
```

selfInvocation에는 @Transactional이 없다. 이 메서드가 같은 객체의 failRuntime을 직접 호출하므로 failRuntime 앞의 트랜잭션 프록시를 다시 거치지 않는다.

```text
외부에서 selfInvocation 호출
  → 서비스 전체 트랜잭션 없이 내부 failRuntime 실행
  → Repository.saveAndFlush의 자체 트랜잭션 시작
  → 저장소 호출이 정상 종료해 커밋
  → 그 다음 서비스 코드에서 RuntimeException 발생
  → 이미 끝난 저장소 트랜잭션은 이 예외로 소급 취소되지 않음
```

이 실험은 “서비스 트랜잭션이 없어도 저장소 자체의 트랜잭션으로 저장될 수 있다”는 뜻이다. JPA가 아무 트랜잭션 없이 변경 SQL을 마음대로 확정한다는 뜻은 아니다. 외부 트랜잭션이 이미 있다면 결과 조건도 달라진다.

근거: [트랜잭션 프록시의 내부 호출 제한](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html), [저장소 기본 트랜잭션](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html).

## 9. 주문 한 건과 주문 항목 두 건은 어떻게 다른가?

PurchaseOrder는 주문 전체를 나타낸다. OrderLine은 그 주문에 들어 있는 메뉴 한 종류와 수량을 나타낸다.

```text
PurchaseOrder
  customer = "김학생"
  lines = [아메리카노 2개, 카페라떼 1개]

DB:
  practice_order       → 주문 행 1개
  practice_order_line  → 주문 항목 행 2개
```

여기서 아메리카노 2개는 수량이 2인 항목 하나다. 주문 항목 행 두 개로 나눈다는 뜻은 아니다.

### 주문 생성 서비스 한 줄씩 읽기

```java
@Transactional
public OrderResponse create(String customer) {
    PurchaseOrder order = new PurchaseOrder(customer);
    order.addLine(new OrderLine("아메리카노", 2));
    order.addLine(new OrderLine("카페라떼", 1));
    orders.saveAndFlush(order);
    return toResponse(order);
}
```

| 줄 | 실행 내용 |
|---|---|
| @Transactional | 외부에서 프록시로 호출할 때 이 처리 범위를 트랜잭션으로 실행 |
| create(String customer) | 주문자 문자열을 받아 OrderResponse 반환 |
| new PurchaseOrder(customer) | 주문자 값을 가진 새 주문 객체 생성 |
| new OrderLine("아메리카노", 2) | 메뉴 이름과 수량을 가진 새 항목 객체 생성 |
| order.addLine(...) | 주문 목록과 항목의 주문 참조를 함께 연결 |
| orders.saveAndFlush(order) | 주문 저장 처리와 변경 동기화 |
| return toResponse(order) | 엔티티 값을 응답 record로 변환해 반환 |

실제 서비스 메서드에서 return을 실행한 다음 프록시가 커밋을 마치고 호출자에게 결과를 전달한다. 따라서 메서드 안에서 응답 DTO를 만들 때와 HTTP 응답을 보내는 시점은 다르다.

### addLine은 자바 객체의 양쪽 관계를 맞춘다

```java
public void addLine(OrderLine line) {
    lines.add(line);
    line.assignOrder(this);
}
```

첫 줄은 현재 주문의 항목 목록에 line을 넣는다. 둘째 줄은 line이 자신이 속한 주문을 참조하게 한다. this는 현재 PurchaseOrder 객체다. OrderLine의 order_id 외래 키는 그 주문을 가리킨다.

이 메서드는 관계를 맞추는 자바 코드다. DB에 함께 저장되게 하는 별도 설정은 다음 cascade다.

## 10. cascade=PERSIST — 부모 저장을 자식에게 전달

```java
@OneToMany(mappedBy = "order",
        cascade = CascadeType.PERSIST,
        orphanRemoval = true)
private List<OrderLine> lines = new ArrayList<>();
```

| 부분 | 의미 |
|---|---|
| @OneToMany | 주문 하나에 주문 항목 여러 개 |
| mappedBy = "order" | 관계의 외래 키 관리는 OrderLine의 order 필드를 기준으로 함 |
| cascade = PERSIST | 주문에 persist를 적용할 때 연결된 새 항목에도 persist 전달 |
| orphanRemoval = true | 관리 중인 관계에서 제거된 자식을 삭제 대상으로 처리 |
| new ArrayList<>() | 자바에서 항목을 보관할 빈 목록 생성 |

**cascade는 영속성 연산의 전파**다. 쉽게 말하면 “부모에게 한 저장 처리를 연결된 자식에게도 적용한다”는 뜻이다. 모든 작업이 전부 전파되는 설정은 아니며, PERSIST는 저장 등록 연산의 전파를 의미한다.

이 예제는 새 주문의 id가 없으므로 저장 시 persist로 처리하고 새 주문 항목들도 함께 저장한다. 새 주문을 저장했을 때 자식 두 건까지 저장되는 이유가 PERSIST 설정이다. 같은 코드가 언제나 merge까지 전파하는 것으로 외우지 않는다. 관계 설정과 새 객체 여부에 따라 구분해야 한다.

cascade는 DB의 외래 키 ON DELETE CASCADE 설정과도 다르다. 여기서는 JPA가 적용하는 엔티티 연산 규칙이다.

근거: [Jakarta Persistence — persist 전파와 관계 매핑](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html).

## 11. orphanRemoval — 주문에서 빠진 항목 삭제

**고아 객체(orphan)**는 이 설정의 문맥에서 소유 부모의 관계에서 빠진 자식 엔티티를 뜻한다. 자바 변수에서 참조가 없어져 메모리가 정리되는 일과는 다르다. 여기서는 실제 DB 삭제 대상이 되는지를 다룬다.

수업의 removeLine은 다음 순서로 동작한다.

```java
public void removeLine(Long lineId) {
    OrderLine line = lines.stream()
            .filter(item -> item.getId().equals(lineId))
            .findFirst()
            .orElseThrow(() -> new NoSuchElementException("주문항목 없음"));
    lines.remove(line);
    line.assignOrder(null);
}
```

| 코드 | 말로 읽기 |
|---|---|
| lines.stream() | 주문 항목들을 순서대로 처리할 스트림 생성 |
| filter(...) | 항목 id가 전달한 lineId와 같은 항목만 선택 |
| findFirst() | 선택 결과 중 첫 번째 항목을 Optional로 받음 |
| orElseThrow(...) | 항목이 없으면 예외 발생 |
| lines.remove(line) | 현재 주문의 자바 목록에서 항목 제거 |
| line.assignOrder(null) | 항목 쪽 주문 참조도 해제 |

서비스는 관리 중인 주문을 조회해 이 메서드를 호출하고 orders.flush()로 변경을 동기화한다. orphanRemoval=true가 있으므로 제거한 항목은 DB 삭제로 이어진다. 주문 참조를 null로 두는 줄이 있다고 최종 결과를 “외래 키만 NULL로 저장한다”라고 읽으면 안 된다. 수업의 의도는 그 자식 행 자체를 삭제하는 것이다.

**쉽게 풀면:** 주문을 유지하면서 그 안의 특정 항목을 없앤다. 단순히 자바 목록만 바꾸는 데 그치지 않고 설정에 따라 DB의 항목도 제거된다.

이 기능은 부모에 종속된 자식에 적합하다. 여러 부모가 공유해야 하는 데이터를 관계에서 뺐다는 이유로 삭제하도록 적용하면 안 된다. 또 준영속·새 객체 등 모든 상태에 똑같이 적용하는 규칙이 아니라 관리 중인 관계의 변경을 전제로 이해한다.

### 부모 주문을 지우면 항목도 삭제되는 이유

이 매핑의 orphanRemoval=true는 부모 자체를 remove하는 경우의 자식 삭제 전파도 규정한다. 따라서 이 예제는 cascade=REMOVE를 별도로 적지 않아도 부모 삭제에 따라 소유한 항목이 삭제될 수 있다. **cascade=PERSIST만으로 자식 삭제까지 해결된다고 설명하면 틀린다.**

근거: [Jakarta Persistence — orphanRemoval 규칙](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html).

### OrderLifecycleTests의 검사 두 가지

첫 테스트 cascadePersistAndOrphanRemoval은 다음을 확인한다.

1. orders.create(...)로 주문 생성
2. 다시 조회한 주문의 항목 수가 2인지 확인 → 부모 저장 시 자식 저장 전파 확인
3. 첫 항목의 id를 기억하고 removeLine 호출
4. 다시 조회한 주문의 항목 수가 1인지 확인
5. 별도 EntityManager로 그 OrderLine을 찾아 null인지 확인 → 목록에서만 빠진 것이 아니라 DB에서도 삭제되었는지 확인

둘째 테스트 deletingParentAlsoDeletesOwnedLines는 주문을 삭제한 뒤 항목 각각이 조회되지 않는지, 이번 테스트 주문 수도 0인지 확인한다.

별도 EntityManager를 만들면 앞에서 관리하던 객체만 보고 판단하지 않고 별도 조회로 확인할 수 있다. 테스트 전체가 하나의 롤백 트랜잭션에 묶여 있지 않으므로 서비스가 마친 결과를 검사하는 구조다.

## 12. record와 응답 변환을 읽기

수업의 응답 타입 일부는 다음과 같다.

```java
public record LineResponse(Long id, String menuName, int quantity) {}
```

record는 데이터를 담는 자바 클래스를 간결하게 선언하는 문법이다. 각 구성 요소의 private final 필드, 생성자, 읽기 메서드, equals·hashCode·toString 등이 제공된다.

```java
LineResponse line = new LineResponse(10L, "아메리카노", 2);
Long id = line.id();
String name = line.menuName();
int quantity = line.quantity();
```

record의 읽기 메서드는 getId()가 아니라 id() 형태다. 10L은 long 정수 값의 자바 표기이며 Long으로 전달할 수 있다. record라는 이유만으로 JPA 엔티티이거나 DB에 저장되는 것은 아니다. 이 예제에서는 응답 DTO다.

```java
order.getLines().stream()
        .map(line -> new LineResponse(
                line.getId(), line.getMenuName(), line.getQuantity()))
        .toList()
```

위는 OrderLine마다 필요한 값을 읽어 LineResponse를 만들고 새 응답 목록으로 모은다. map은 요소 변환, toList는 결과 목록 구성이다. 주문 엔티티를 목록에서 없애거나 DB를 수정하는 코드가 아니다.

**쉽게 풀면:** 내부에서 관리하는 엔티티의 값을 읽어서 외부에 전달할 모양으로 다시 구성한다. record의 final 필드는 재대입을 막지만 그 안에 담긴 List의 내용까지 항상 완전 불변으로 만드는 것은 아니다.

근거: [Java 21 record 공식 설명](https://docs.oracle.com/en/java/javase/21/language/records.html).

## 13. AuditingTests — 저장·수정 시각 확인

BaseTimeEntity는 생성·수정 시각 필드를 공유하는 부모 클래스다. 별도의 BaseTimeEntity 테이블에 저장한다는 뜻은 아니다.

| 설정 | 이 예제의 역할 |
|---|---|
| @MappedSuperclass | 하위 엔티티에 필드 매핑 상속 |
| @EntityListeners(AuditingEntityListener.class) | 엔티티의 저장·수정 이벤트에 auditing 처리 연결 |
| @CreatedDate | 생성 시각 기록 |
| @LastModifiedDate | 수정 시각 기록 |
| Application의 @EnableJpaAuditing | auditing 기능 활성화 |

PurchaseOrder가 BaseTimeEntity를 상속하므로 주문의 생성·수정 시각을 읽을 수 있다. 기본 설정에서는 생성 시 수정 시각도 함께 채워질 수 있다.

AuditingTests는 주문 생성 후 다시 읽고 두 시각이 null이 아닌지 확인한다. 잠시 기다렸다 주문자를 바꾼 뒤 생성 시각은 그대로이고 수정 시각은 나중인지 검사한다. 잠시 기다리는 이유는 비교할 시각 차이를 만들기 위해서다.

근거: [Spring Data JPA auditing](https://docs.spring.io/spring-data/jpa/reference/auditing.html).

### 현재 rename 소스에서 반드시 구분할 줄

현재 파일에는 다음 코드가 있다.

```java
PurchaseOrder order = findEntity(id);
order.changeCustomer(customer);
orders.saveAndFlush(new PurchaseOrder(customer));
return toResponse(order);
```

첫 두 줄은 기존 주문을 찾아 주문자를 바꾼다. **셋째 줄은 기존 주문을 동기화하는 표현이 아니라 새 PurchaseOrder를 만들어 추가 저장하는 코드**다. saveAndFlush의 flush 과정에서 기존 주문 변경도 반영될 수 있지만 새 주문 INSERT도 요청한다.

주문자 변경이 목적이라면 다음과 같은 형태로 이해해야 한다. 아래는 설명을 위한 수정 예시이며 실제 수업 소스 파일은 변경하지 않았다.

```java
@Transactional
public OrderResponse rename(Long id, String customer) {
    PurchaseOrder order = findEntity(id);
    order.changeCustomer(customer);
    orders.flush();
    return toResponse(order);
}
```

이미 관리 중인 order는 변경 감지 대상이므로 새 주문을 만들 필요가 없다. 여기서 flush를 유지하면 수정 시각 등 동기화 시점의 값을 응답에 담는 의도도 표현할 수 있다.

현재 auditing 테스트는 시각만 검사하고 “이름 변경 뒤 주문이 추가되지 않았는지”는 검사하지 않는다. 그래서 그 검사만으로 잘못된 추가 저장까지 없다고 보장할 수는 없다. **테스트가 확인하는 항목과 메서드의 모든 동작은 구분해야 한다.**

## 14. 예외 처리 클래스와 트랜잭션 테스트는 다른 흐름이다

7장 GlobalExceptionHandler는 HTTP 요청 처리 중 NoSuchElementException을 404로, IllegalArgumentException과 MethodArgumentNotValidException을 400으로 바꾼다.

- 주문이 없거나 항목을 찾지 못함 → NoSuchElementException → HTTP 처리에서는 404
- 수량이 1 미만이거나 가격 범위가 잘못됨 → IllegalArgumentException → HTTP 처리에서는 400
- @Valid 요청 검증 실패 → MethodArgumentNotValidException → 400

반면 TransactionTests는 HTTP 요청을 보내는 코드가 아니라 주입된 서비스를 직접 호출한다. 따라서 assertThrows로 잡는 예외를 ControllerAdvice가 중간에서 JSON으로 바꾸는 흐름이 아니다.

**쉽게 풀면:** 트랜잭션 규칙을 시험할 때는 서비스 호출과 DB 결과를 보고, HTTP API 오류를 처리할 때는 별도의 예외 처리 클래스가 응답 모양을 만든다. 예외라는 같은 단어가 나와도 어느 경로에서 다루는지 봐야 한다.

## 16. 본문 흐름과 별도로 모은 메모

### ddl-auto: validate

7장 설정은 spring.jpa.hibernate.ddl-auto=validate다. 시작할 때 JPA 매핑에 필요한 DB 테이블·컬럼 등이 맞는지 검사하고, 맞지 않으면 애플리케이션 시작이 실패할 수 있다. 테이블을 자동으로 만들거나 고쳐 주는 설정은 아니다. 행의 데이터 내용이 전부 올바른지 검사하는 기능도 아니다.

| 설정 | 일반적인 의미 |
|---|---|
| none | 자동 생성·수정 안 함 |
| validate | 스키마와 매핑 적합성 검사 |
| update | 스키마 변경 시도 |
| create | 초기화 때 스키마 삭제·재생성 |
| create-drop | 생성하고 정상 종료 때 삭제 |

**쉽게 풀면:** validate는 “이미 준비된 DB 구조로 실행할 수 있는지 확인”이다. 따라서 7장을 실행하려면 필요한 실습 테이블을 먼저 준비해야 한다. 이번 정리를 위해 애플리케이션을 실행하거나 테이블을 바꾸지는 않았다.

근거: [Spring Boot DB 초기화](https://docs.spring.io/spring-boot/how-to/data-initialization.html).

### 현재 메뉴 검색 코드에서 구현된 범위

7장의 메뉴 검색 API는 keyword·minPrice·maxPrice·categoryCode를 받는다. 하지만 현재 MenuSpecifications.search는 keyword의 이름 검색 조건만 구성한다. 나머지 세 인자를 받았다고 SQL 조건까지 자동으로 추가되는 것은 아니다.

MenuService는 음수 가격과 뒤바뀐 가격 범위를 검사하지만, 이 검사는 검색 SQL에 가격 WHERE를 붙이는 작업과 다르다. 가격·카테고리 검색을 완성하려면 Specification에 해당 조건식을 추가해 결합해야 한다.

또 현재 MenuService.search에는 @Transactional이 없고, MenuResponse.from은 LAZY 카테고리의 이름을 읽는다. open-in-view=false이고 별도 외부 트랜잭션도 없는 일반 HTTP 흐름에서는 Repository 반환 후 지연 로딩 오류가 생길 수 있다. 예를 들어 서비스 검색 메서드에 읽기 전용 트랜잭션을 적용해 DTO 변환까지 관리 범위에 두고, 조회 수를 줄이려면 적절한 fetch 전략도 설계할 수 있다. 트랜잭션만 추가한다고 N+1까지 자동으로 해결되는 것은 아니다.

이는 현재 소스를 읽어 확인한 구현 범위와 동작 조건이다. 입력 항목이 있다는 이유만으로 모든 검색 조건이 이미 구현되었다고 외우지 않는다.

### 메모의 C·S·R 복습을 더 정확하게 고치기

| 메모 | 보완한 설명 |
|---|---|
| C는 HTTP 요청을 받아 DTO로 매핑한다 | Controller는 요청 인자를 받고 응답을 연결한다. JSON→DTO 변환은 주로 Spring 메시지 변환기가 수행한다. |
| S는 DTO를 Entity로 변환한다 | Service는 업무 규칙·처리 순서·트랜잭션을 다룬다. DTO와 엔티티 변환은 그 일부다. |
| R은 Entity로 DB 데이터를 주고받는다 | Repository는 엔티티 접근과 쿼리 실행 기능을 제공한다. 네이티브 조회는 엔티티 전체 대신 프로젝션을 반환할 수도 있다. |

### 문서에서 자주 쓴 짧은 용어

| 용어 | 쉬운 풀이 |
|---|---|
| 매핑 | 서로 다른 표현 사이에서 어떤 값을 연결할지 정함 |
| 바인딩 | 이름·위치가 있는 값 자리에 실제 인자를 연결 |
| getter | 객체의 값을 읽는 메서드 |
| 프록시 | 호출 앞뒤에 처리를 적용하거나 값을 읽을 구현을 제공하는 객체 |
| 영속 상태 | 현재 JPA 관리 환경이 추적 중인 상태 |
| 트랜잭션 경계 | DB 작업을 함께 확정·취소할 범위 |
| cascade | 연결된 엔티티에 특정 영속성 연산 전달 |
| orphanRemoval | 관리 중인 소유 관계에서 빠진 자식의 삭제 처리 |
| fixture | 테스트에 필요한 준비 데이터·환경 |
